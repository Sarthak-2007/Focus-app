### 4.5 DONE is an event (Rurik — DONE semantics)

The DONE press fires one `@Transaction` on DOWN — it does not wait
for the choreography. The transaction inserts an append-only

no resurrection. **Un-complete is symmetric:** it deletes that task's

downstream surface drops the task automatically, because none of them
stored it. Completion-events land in migration **9→10**.

#### 5.3.4 Accrual, banks, slip and drain (Barriere, verbatim numbers)

State, exactly: `banked ∈ {0, 15, 30, 45}` · `held` = seconds accrued
above `banked` in the current contact · owed = `60 − banked − held`.
Accrual runs only while contact is live, at 1.0×, sampled on the
existing 32ms loop. The fill is **direct-drive linear** — an eased
timer is a lying timer.

- **Per-second tick:** haptic `[0, 10]ms @ 140 (≈0.55)`, sound none.
  (This replaces the SCORE's inter-bank tooth on this surface.)
- **5-second metronome:** haptic `[0, 12]ms @ 205 (≈0.8)`, replacing
  that second's tick. Twelve pulses = the minute, countable in the
  thumb.
- **Final leg (45→60):** the tick grows to `[0, 12]ms @ 180`; at 55s
  each remaining second's tick doubles (second pulse +100ms).
  Chamber 4's walls step brighter at each of the last 5 seconds
  (100ms step each). **Drain rules do not change in the final leg.**
- Sync law: haptic onset and sound onset within **±8ms**; the visual
  pair lands in the same 100ms window.

**The bank frame:** at each bank crossing, everything lands on **one
frame** — chamber wall **3→5dp** and chamber floor line **1dp→3dp**;
chamber fill **hard-cuts to solid banked** (solid + toothed = banked
and safe; smooth + alpha = live and at risk); an **8dp step-tooth
drops** from the chamber's top edge; the next notch fills; the margin
word **re-strikes** (`BANKED 15 / 30 / 45`); the **40ms bank-catch
freeze** (Register spectacle ledger #4); sound + haptic per the table.
**Pitch falls, weight rises** — Barriere's fixed set replaces the
SCORE's rising LADDER set on this surface:

| Bank | Haptic (ms / amplitude 0–255) | Sound | dB vs seal |
|---|---|---|---|
| **15** | `[0, 12, 28, 10] / [0, 215, 0, 160]` | 560Hz transient, 16ms, gain 0.54 | ≈ −5.4dB |
| **30** | `[0, 14, 22, 11, 20, 12] / [0, 235, 0, 175, 0, 155]` | 470Hz, 22ms, gain 0.58 | ≈ −4.7dB |
| **45** | `[0, 17, 26, 13, 22, 14] / [0, 255, 0, 200, 0, 170]` | 390Hz, 28ms, gain 0.62 | ≈ −4.2dB |

(Fixed per bank = a timbre grade; pitch as melody/formula stays dead.
Barriere's within-segment pitch climbs — 420→660Hz per segment,

**Floors never drain in-session.** A bank lives while the overlay is
open and across dismissal/re-entry within the same session (the bank
is the session's, held in the ViewModel); it clears only on (a)
completion, (b) an explicit exit-chip tap, or (c) the session ending
on its own. It never expires on a hidden timer.

**Slip and drain:**
1. **0–800ms after contact loss: no drain, no accrual.** Grace is
   **per-slip and uncapped** — grace never accrues a held millisecond
   and the phone stays sealed throughout.
2. **Drain ramp: 1.0× for the first 3.0s of drain → 2.0× thereafter,**
   easing back as the floor catch approaches. A hand back at 3.0s has
   lost **≈2.2s** of tail; a walk-away loses the whole tail: worst
   tail (≈14.9s unbanked) reaches the floor in **≈9.7s** from the
   slip (0.8 grace + 3.0 @ 1.0× + ≈5.9 @ 2.0×).
3. **Floor = the last bank, full stop.** Drain halts dead at
   `banked`; if `banked = 0`, the floor is 0. No zeroing clause
   exists.
4. **Re-grab:** drain halts within one 32ms frame of new contact;
   accrual resumes after a **250ms re-seat** (the re-seat does not
   accrue). A skid the sensor reports as a "new" touch beginning
   inside the bar within the grace window is a continuation, never a
   fresh start.
5. **OS cancels** (call UI, system gesture) are slips — grace +
   drain — never completions, never instant zeroes. If the system
   dismisses the overlay mid-hold, the bank persists for re-entry
   within the same session.

**The drain is felt, not watched:** during drain, a haptic pulse
every **250ms** — `[0, 6]ms`, amplitude falling linearly **150 → 60**
as the tail empties — over a descending sound glide **600Hz →
280Hz**, gain 0.34 → 0.18. At the floor: a **catch** — latch waveform
`[0, 11, 26, 9] / [0, 215, 0, 150]` at ×0.7 gain, 520Hz. If the floor
is 0, the drain ends with the latch-release pattern instead.
**Drain-stop rendering (Floor's requirement, inside the valve per
Freya's one-rendering rule):** when the drain stops at the floor, the
valve's own centre line states `SLIPPED — BANKED {n} SAFE` for 2s.
The overlay card renders nothing about the slip.

#### 5.3.8 The token behind the valve (TOKEN-SPEC, FINAL as folded)

**The token is a fact, not a counter.** It is **derived from an
append-only spend ledger**, never held as a number anywhere. New Room
table `emergency_break_spends` — no update, no delete path anywhere
in the app: `id` INTEGER PK AUTOINCREMENT · `sessionId` INTEGER NOT
NULL (the `FocusSessionEntity.id` this break ended; the join key) ·
`spentAtWallMillis` INTEGER NOT NULL · `weekAnchorMillis` INTEGER
NOT NULL (the Monday-00:00 anchor of the week this spend counts
against — **stored at spend time, never recomputed**) ·
`heldSeconds` INTEGER NOT NULL (always 60 at completion today). No
other columns — **no attempt rows, no bank rows, no counter row**.
DAO additions, names final: `insertEmergencyBreakSpend` ·
`getSpendsForWeek(anchor)` · `observeSpendsForWeek(anchor)` ·
`getAllSpendsSnapshot()`. The only formula in the system:

```
remaining(now) = max(0, 1 − getSpendsForWeek(weekAnchorMillis(now)).size)
```

**TOKEN: exactly 1 per week** (Register).

**The week anchor — Monday 00:00.** One shared definition,
`MonolithWeek.weekAnchorMillis(nowMillis, zone =
ZoneId.systemDefault())`: the instant of **Monday 00:00:00.000 local
civil time** of the week containing `now`, in the device's current
zone. Consumed by the token and by any weekly rendering — one fact,
one definition. Rollover needs no job, no reset, no alarm. Edge cases
ruled in TOKEN-SPEC §3 and carried whole: **travel / timezone
change** — anchor always computed in the current zone; a zone change
shifts the effective refill by at most the zone difference (bounded
≈26h), accepted deliberately. **DST** — `atStartOfDay` java.time
rules. **Clock changes** — spends are rows; moving the clock back
deletes nothing. **Scope** — `MonolithWeek` does not replace
`RoutineSchedule`; spends attribute by *completion* instant, routine
windows by *start* day; the Monday refill resets no routine streak.
**Direct Boot** — the DB lives in device-protected storage, so
`remaining()` is computable before first unlock.

**The only write.** At valve completion, and nowhere else, the
repository runs **one transaction**, `completeEmergencyBreak():
BreakResult` (sealed type, exactly three outcomes):

1. `active = dao.getActiveSessionSnapshot() ?: return NoActiveSession`
2. `if getSpendsForWeek(currentAnchor).size >= 1 return
   RefusedNoToken` — the session stays sealed.
3. Insert the spend row (`sessionId = active.id`, `spentAtWallMillis
   = now`, `weekAnchorMillis = currentAnchor`, `heldSeconds = 60`).
4. Disarm, dispatched on the active session's kind, inside the same
   transaction: a *routine session* books by Sten's attendance outcome
   (ATTENDED as booked / PARTIAL via `disarmRoutineSessionPartial` /
   MISSED via `disarmRoutineSessionUnattended`, `finalizeAttendance`
   in-transaction; SLEEP-loadout routines exempt — generic path, no
   finalise); *any other session* disarms via
   `disarmActiveSession(completed = false, outcomeReason =
   EMERGENCY_BREAK_REASON)`. The generic path's wall-clock booking
   (Lie #13) must never run on a routine session.
5. `return Completed`.

**The boundary race:** a hold that starts Sunday 23:59 and completes
Monday 00:01 spends against **the anchor of the completion instant**
— the new week pays. Ruled.

**Attempts write nothing — verified, now required (HPA-28).** Bank
crossings write nothing; slips, drains, abandoned attempts, OS cancels
write nothing; the overlay merely *opening* writes nothing. **No
attempts counter may be added.** This silence governs
`emergency_break_spends` and token accounting only: it does **not**
reach `routine_attendance` (Sten §5.3). The record of the valve is
binary per week: a spend row, or silence. **Grace cancel is not a
break:** the Accidental Start Grace Cancel path is untouched — no
spend row, no spend check, zero-booking preserved; it never passes
through `completeEmergencyBreak()`.

`sessionId` is the join between the spend ledger and the session row,

### 6.7 PARK — the invocation contract

*This subsection states the contract. PARK's contents and board are
§8's; the detail mechanics below are Mikro's, which govern where this
contract is silent.*

**What PARK is:** a utility end-detent inside the track at the
rail's right end, after LEDGER — a **position, not a stop**: no
segment rhythm, no destination word printed in the zone (§6.4). It is
where the rested user puts the machine down between runs: the repair
board, sound and theme live behind it (§8), and nothing behind it is
a daily journey. PARK costs a flat **48dp** under every variant
(44dp zone + 4dp notch; Register).

**Invocation — arrival IS the invocation.** The cap is dragged past
LEDGER into the zone: rising resistance in the last 12dp (Kin's
resistance map, gentle class — the finger still wins), the grip
notch stepping ink-35 → ink-70 as the cap crosses the zone's inner
edge, a detent tick at zone entry pitched *below* the stop family —
it is not a stop and must not sound like one (the exact pitch is
Ton's to assign; Mikro's flag to him stands open). On the cap's seat
against the end-wall (soft detent, 4ms, duller than a stop seat), the
drawer rises on that same frame — **KIN-DRAWER, 280ms** (Register
amendment: open 280ms SEAT, close 160ms THROW). **There is no second
tap, no handle tap, no confirm.** A tap on the PARK zone does the
same, priced identically: DOWN answers by the notch stepping ink-35 →
ink-70 the same frame; on release the cap runs the 48dp leg powered,
counted with PARK as one step under the KIN-NAV formula, and
invocation waits for the seat — a tap never opens the sheet
mid-glide. The second lawful path is the Guard line's tap while
unsealed (§6.2) — it sends the cap to PARK under the same travel law,
and the seat is the invocation, whatever the input. **First run**
opens PARK directly (§8.10-12). No other surface invokes PARK, and in
any branch without the dissolution PARK does not exist at runtime —
build-time absence, never a greyed zone.

**While open:** the cap stays parked in the zone for as long as the
drawer is open — the drawer is visibly the cap's cargo. No stop word
changes state: LEDGER does not ink, no stop claims selection;
position alone says where the cap is. The drawer has exactly **two
rest heights, closed and open** — no half-detents, no peek height;
inner rows are visible from frame one, no stagger, no fade-in of
rows, and **the sheet's rows are operable only from the open seat
frame** — a row tapped mid-rise is not answered. Handle law: DOWN on
the open sheet's grab strip — the strip's centre grip line steps
ink-55 → ink-100 and widens 24 → 28dp the same frame; the sheet's top
8dp band drops one tone step; no sheet movement on DOWN. Drag: the
sheet follows **1:1** vertically, clipped. Release **above 40%** of
open height seats **open**; **below 40%** seats **closed** — both
under KIN-SNAP scaled to the remaining travel. Grab strip: **visual
32dp, touch 48dp** (Mikro F-F, resolved at merge by the touch/visual
split — Razor's 32dp is the drawn strip, the Register's floor is its
target). Open seat frame: grip line back to 24dp / ink-70, top band
tone restores, feel 4ms. Closed seat frame: the notch returns to
ink-35, the cap is freed.

**Dismissal is one gesture with leaving:** exactly three inputs, each
a single gesture that does both — (1) **a stop press / cap drag
out:** the sheet dismisses and the cap departs **on the same input**;
the cap seats on the chosen stop under §6.4's law; (2) **drag the
sheet down past 40%** → it seats closed; the cap returns to the stop
it came from; (3) **tap on the scrim / content above the sheet, or
tap PARK again** → the sheet seats closed over a **160ms exit**; the
cap travels home to the current stop under the KIN-NAV formula
counted from PARK. Leaving PARK and dismissing the drawer are never
two gestures, two animations owned by two systems, or a state where
the cap is home and the drawer still up.

**While sealed, PARK cannot open** (§6.1): no invocation path
answers, and the drawer does not tease a closed state over a running
session.

### 7.1 Sealed-state law (this surface)

While a session is sealed: the Drawer is read-only furniture. It can
be read — a stored row and its detail may be opened and read in full
— but search input, reopening, and every edit are inert until the
session ends. Nothing in the Drawer accepts input, offers a decision,
or changes state mid-session. (How he *reaches* it mid-session is
§6.1's ruling: travel dies at the seal; an already-open Drawer
degrades to this read-only form.) The search field renders as print
while sealed and answers nothing (§7.10's thirty-day promise is
lawfully suspended for exactly the sealed hours, and §7 states the
exception rather than hiding it).

### 7.2 What is stored — the one content law

The Drawer reads **completed task rows only** — never the session's
`completedTasksSummary` string, which would be the same fact in a
second form. When a task becomes **COMPLETED**, retain:

- the task's internal ID, for identity only;
- **title**, exactly as it stood at completion;
- **category**;
- **notes / substeps**, exactly as stored with the task;
- **estimated minutes**;
- **actual seconds spent**;
- **completion timestamp** — the sort key and the stored date/time;
- **completed-in-session ID**, as internal provenance only; it is not
  printed as a score or code.

Nothing else is Drawer content. Sessions, holds, deflections, and
breaks are not stored here (§7.8); the finish receipt remains their
moment. The feed is §4.5's completion event — the same transaction
that drops the row below Tasks' foundation line stores it here,
exactly once.

**Retention is permanent.** A stored task is never auto-deleted,
expired, pruned, or cleaned up by age — years of finished tasks stay
(his add-on, Oct 29, 07:38: *"Even after years etc."*). There is **no
Clear control** for completed tasks in Tasks or in the Drawer, and no
code path in the Drawer that deletes by date. §7.10 makes permanence
an auditable property, not a promise — including its one dependency:
the destructive-migration fallback (§5.3.8) must land before the
permanence test can pass.

**Completion is not an achievement event.** It earns no point,
streak, badge, percentage, or total. If a task is deliberately
reopened, it is no longer finished and leaves the Drawer; if it is
completed again, it returns under the **new** completion timestamp.
(The reopen act's home surface is not named by the ruling — §9,
charge B-30; the repository toggle exists and the Drawer detail here
is read-only. Flagged, not invented.)

**Two honest limits of the word "permanent," printed because §7 is
where he will look for the promise:** permanent means *the app never
deletes by age*. It does not mean *survives the phone*. The record is
a local database; the AES backup blob's only consumer was its own
READY badge (§0.1-10 — killed as a dead payload, no egress, no
restore). If the phone is lost or the app uninstalled, years of
stored tasks go with it, and no sentence in §7 may imply otherwise. A
real export/restore — and any cross-device life for the Drawer while
his sync feature stands held by his own order — is a feature decision
for him, not a Drawer fix (§9, charge B-56).

### 7.3 How the Drawer opens

- **Header:** `STORED`, with one search field: `TYPE TO FIND A
  TASK`. The field's touch height meets the 48dp floor (Register,
  touch floors) — retrieval is the Drawer's one act, and it is not
  specced below the app's floor.
- **Default view:** the current month's finished tasks, newest first,
  grouped under plain date headings such as `THU 29 OCT`. A date
  heading is a shelf label only — no total, grade, or verdict follows
  it. Today is merely the newest date group, and only if a task was
  finished that day.
- **Browsing by month:** an `ALL MONTHS` index lists one row for each
  month that has at least one stored task — `OCTOBER 2026`, newest
  month first, **label only**. No count or total rides on the row,
  and a month with nothing stored is simply absent. Opening a month
  shows its stored tasks by date, newest first. A month here is an
  **address** for finding things, not a measurement scope.
- **Paging:** within a month, show the newest **50** entries;
  `EARLIER` at the foot loads the preceding 50 (Register: DRAWER
  PAGING 50). The repository pages by completion timestamp and never
  needs to materialise years of rows at once. **Search pages the same
  way** (§7.10 — the silent `LIMIT 200` form is a build error).

### 7.4 Row and detail

- **Row:** task title (up to two lines), category, finish time, and
  time spent. No estimate on the row, no checkbox, no rank, no
  progress bar, no comparison.
- **Detail:** tapping a row opens its stored form — full title,
  category, finish date and time, estimate and actual time as two
  separate plain facts (**never a delta or percentage**), and the
  stored notes/substeps. The detail is read-only (and, while sealed,
  inert per §7.1). Its print form is §7.11's.

### 7.5 Search — what "type stuff" means

**Interpretation, flagged (the ruling's own flag, carried):** the
most plausible reading of his *"and type stuff"* is that, after a
month, he wants to type words to find an old task. The conservative
build includes search and nothing more speculative.

- Search covers **title, category, notes, and substep text**.
- It searches **all stored tasks across all years** (Register: DRAWER
  SEARCH, all years) — not queued work, not future work, and not
  only the month currently open.
- **Multi-word queries, ruled at merge (Old Tom §5.2, Sana adopting —
  flagged for ratification):** the query splits on spaces; **every
  token must match somewhere** in title/category/notes/substeps (AND
  across tokens, OR across fields). One-word behaviour is unchanged —
  §7.10's test passes identically. The ruling's promise was one word;
  he will type two, on the worst day, and the single-literal-string
  form would answer `NOTHING STORED UNDER` for a stored task. Priced
  at ≈ +25 lines + tests, no migration.
- **Wildcards are escaped:** an unescaped `%` or `_` in his typed
  text is SQL pattern, not text. Escape `\`, `%`, `_` and add
  `ESCAPE '\'` per field (≈5 lines). **Not optional** — search must
  search for what he typed.
- Results stay in completion-date order, with the **full date
  including year** on every result. No relevance score and no result
  count are printed. Results page in 50-chunks with `EARLIER` at the
  foot, exactly as months page (§7.10).
- The Drawer does **not** gain post-completion annotations or a
  journal in this build. Notes already stored with the task are shown
  as part of that task. If "type stuff" meant "write a note on an old
  task," that is a separate one-field feature to add only on his
  word.
- This search supersedes Old Tom's earlier search kill for this
  object: that kill assumed an auditor asking only "today?" and "this
  week?" — the frame he has now replaced. Search here is retrieval,
  not tracking. *Named limit, no fix priced:* SQLite `LIKE` folds
  case for ASCII only; a word stored in another script's casing
  conventions may not fold. §7 does not overclaim past this.
- The search field's clear affordance is unspecified in every source
  — carried as a micro-charge (§9, B-52), not invented here.

### 7.10 Findability + permanence (Old Tom's part — the tests)

*Old Tom's history with this object, on the page once: he killed
search for this record (K12) on the ground that an auditor's
questions were "today?" and "this week?" — faces, not queries. His
words replaced that frame: he wants to open the Drawer after a month
and **type stuff**. A kill argued for a different question does not
survive the question changing. What follows is the test the new frame
has to pass.*

**The thirty-day test — one typed word.** Plant (day 0, on device,
through the real Tasks path — no test-harness shortcuts, and never on
the seeded demo completion, §7.10's drill note): finish four tasks,
each carrying one distinctive word in exactly one searched field and
nowhere else — P1 title only · P2 notes only · P3 a substep only ·
P4 category only. Retrieve (day 30 — or, in the build's accelerated
form, the same four rows re-stamped `completedAtMillis` −30 days and
−3 years; the query path cannot tell the difference, and that is the
point): open the Drawer, tap the search field, type the one word.
**Pass, all four plants, every clause:** (1) the plant appears with
**no scrolling through the month** — search is the path; (2) the
result group heading prints the **full date including year**; (3)
results are in completion-date order, newest first — no relevance
order, no score; (4) **no result count is printed** — not before, not
after, not as a footer; (5) a word stored nowhere returns exactly
`NOTHING STORED UNDER “<query>”`. **Pre-committed consequence:** if
P2 or P3 fails, the search is reading fewer fields than §7.5 promises
and §7 does not ship until the query covers title, category, notes
**and** substep text. If P1 fails, nothing else in this section
matters until it passes. *The standing form of this test:* Old Tom's
demote-era condition — *if six months of his actual behaviour show a
Sunday audit that goes looking for the record and cannot find it, the
demote has failed* — survives the tab's keeping as a **standing
acceptance test, not a reversal trigger**. There is no longer a
placement to reverse. The drill above is the Sunday audit, mechanised;
it runs at build, and re-runs whenever the Drawer or the task store
is touched. What it can trigger now is a build failure: §7 does not
ship, or ships named as failing, until retrieval passes.

**The all-months test — two taps, any month, any year.** From the
Drawer landing: tap `ALL MONTHS` (tap 1), tap the month row (tap 2).
The month's stored tasks are on screen. **Two taps is the whole
budget** — a third tap, a scroll through a calendar grid, or a
year-picker fails it. The index lists **one row per month that holds
at least one stored task, newest month first, label only**. The index
is derived from the stored rows themselves (`getStoredMonths()`) —
never from a separately maintained list that could drift. Test both
directions, including a row stamped 23:5x on a month's last day and
00:0x on the next month's first — SQLite's `'localtime'` month
bucketing is the one thing renders cannot see; **that check runs on
the phone, near midnight, once, before this section is called done.**
Inside a month: newest 50, `EARLIER` loads the preceding 50, no row
skipped or doubled at the seam (the `id DESC` tiebreak is
load-bearing).

**Permanence — an auditable property, not a promise.** The grep
list (all must come back as stated, run at every round's end by the
invariants owner):
1. `clearCompletedTasks` — **zero hits, all four links of the
   chain**: the DAO delete (`DELETE FROM focus_tasks WHERE status =
   'COMPLETED'`), the repository wrapper, the ViewModel function, the
   Tasks-screen wiring. Unrendered is not removed — a live chain one
   chip away from resurfacing is a deletion waiting for a deadline.
2. Every `DELETE FROM focus_tasks` in the tree, read by a human, one
   by one: **none may carry a date, age, batch, or status predicate
   that can reach a COMPLETED row.** `deleteTaskById` survives only
   as the queue's per-task delete-with-undo for *uncompleted* rows —
   its call sites are audited to prove no stored row can reach it.
3. No retention machinery exists: no cleanup job, no expiry field, no
   "prune," no WorkManager periodic task touching `focus_tasks`. The
   absence is the feature; grep is how absence is evidenced.
4. **The one reachable wipe that is not the Drawer's code:**
   `fallbackToDestructiveMigration(true)` — a failed migration
   destroys every stored task at once. TOKEN-SPEC §6 owns the
   migration and the fallback's removal (§5.3.8). **§7's permanence
   test cannot pass until that lands**, and §7 prints that dependency
   rather than borrowing the Drawer build's innocence.

**The runtime drill:** seed rows stamped today, −30 days, −1 year,
−3 years. Open every Drawer path (landing, index, each month, search,
detail), reopen-and-recomplete one *other* task, restart the app,
re-run. Every seeded row still present, still under its own date.
Reopen is the one lawful exit from the Drawer — his hand, on one
task, by name — and the drill proves it is the *only* exit. *Drill
note:* the seeded demo completion (Ruth's Flag B-1, §9 charge B-30)
will sit in the Drawer on first open — a stored task he never
finished. The thirty-day test is run on **his** planted tasks, never
on the seed.

**The never-summons audit (the negative audit).** (1) The Ledger
stop in the band carries **nothing**: screenshot the band on a day a
task was finished and on a day none was — **pixel-identical**. (2) No
notification, no widget figure, no chrome line anywhere reports a
stored count; the `DONE n` tally in the Tasks queue header dies with
the clear chain — grep for it is part of this audit. (3) Inside the
Drawer: month rows carry no counts, date headings carry no totals,
search prints no result count, the header is the word `STORED` and a
search field — nothing else. (4) Nothing in the Drawer changes state
when a task is stored: store a task with the Drawer closed; the
closed Drawer gives no sign. That is not a missing feature. That is
the feature.

**Where the search spec was insufficient — both fixes adopted:**
- **The 200 cap (not optional).** A `searchStoredTasks` ending
  `LIMIT 200`, date-descending, silently deletes the oldest matches
  for any common word — and because no result count may print, he
  cannot even see the truncation. Paged search (§7.5) replaces it:
  `LIMIT 50 OFFSET :offset`, the same `loadEarlier()` the month view
  carries. ≈ +6 lines DAO, +15 ViewModel, +10 screen; no migration.
  Without it, acceptance check 2 below is untestable-as-true for any
  word occurring more than 200 times.
- **Wildcard escaping (not optional)** and **token-split multi-word
  search (adopted, §7.5)** — as ruled there.

**How a kept tab still buries — printed so the Drawer cannot fail
him quietly:** (1) **the word in his head is not the word in the
row** — search finds only words actually stored; the spec's real
defence is four fields searched, not one, and §7 says plainly that
findability is a property of what was *written* as much as of what is
*searched*; (2) **he remembers two words from two different fields**
— closed by the token-split ruling; (3) **a common word outgrows the
result set** — closed by paged search; (4) **he looks in the wrong
month** — a task finished late on the 31st is remembered as "early
November"; browsing fails and search is the rescue, which is why the
search test outranks the browsing test; (5) **volume buries by
politeness** — in a heavy month the wanted task is three `EARLIER`
presses down a list with no other landmarks; the month view is an
address system, not a reading experience, and §7 does not pretend
otherwise.

*Old Tom's other standing condition — a spent hold prints on the hold
control itself — stands in §5.3.7, where it belongs. It is not Drawer
business and nothing in this section moves it.*

### 7.11 The beauty of the Drawer (Liv's part)

### 7.12 Acceptance checks (this surface — the ruling's seven)

1. A task completed today appears in the Drawer once, under today's
   date, and in no second rendering.
2. Thirty days later, typing a distinctive word from its title or
   notes finds it without scrolling through a month of entries. Years
   later, the same search still reaches it, and the `ALL MONTHS`
   index reaches its month in two taps from the Drawer's landing.
   (§7.10's tests are the operative form of this check — four plants,
   four fields, −30 days and −3 years.)
3. No stored task is ever removed by age, housekeeping, or a
   retention job; there is no code path in the Drawer that deletes by
   date. (§7.10's grep list + runtime drill are the operative form;
   the destructive-migration dependency is printed, not hidden.)
4. No surface in the Drawer prints a day total, week total, month
   total, streak, percentage, chart, rank, or all-time count.
5. A day with no finished tasks produces no zero, no empty grade, and
   no manufactured absence line — a declared word alone may carry a
   heading (§7.6).
6. A declared day word remains a word. It is never converted into a
   number or folded into a total.
7. Nothing in the Drawer calls him back: no badge, no count, no
   notification, no "new" marker. (The band is pixel-identical
   whether or not anything was stored today — §7.10's negative
   audit.)
8. The face passes Liv's render evidence (R1–R6) with no kill
   condition (K1–K6) met — or the Drawer ships in the Residue Face,

### 8.1 Sealed-state law (this section)

While a session is sealed: **the store keeps measuring.** The
heartbeat beats, the bind hooks fire, the log appends — detection is
not a decision, and ignorance is not what HOLD requires. **Nothing
the store learns is announced mid-session** (his verdicts, §0: Q7
stay silent + Q8 the clock runs — one law). The chrome Guard line
does not change, PARK cannot open, no knock, no word, no screen
change; every Android Settings launcher renders as print and answers
nothing (Hale's clause, carried by the ruling — in PARK's case a
repository-level gate, `fixEnabled = !isSessionArmed ∧
missingExists`, the second lock on a door the sealed rail already
closes). The session runs to its scheduled end. At the finish, the
receipt reads the log for the session's window and tells the truth
once: a death recorded inside the window books the session **broken,
never as a clean seal** — and the break is the machine's fault, filed
beside the chain-jams, never against him, and the weekly token is not
spent (he broke nothing). Mid-session renderings of Guard state
freeze at their seal-frame values; the store's *record* never
freezes. PARK holds no slide and no seal path: a session can only be
armed from the Deck, so PARK never has to be closed *by* a seal — it
has to be left before one is reachable. *This supersedes Uhr §5.3's
dead-beat cut to a BROKE screen, filed before those verdicts existed;
Uhr's detection discipline survives, his mid-session rendering does
not.*

### 8.2 The store — one source, no copies

The **Watch Store** is the single source for every permission and
interceptor fact in the app. **No surface runs its own check and no
surface keeps its own copy** — a surface that queries the OS itself,
or caches a verdict past the render that consumed it, is a second
store and a build error (§8.11-1).

**Per item, the store holds exactly three things:**

- **value** — from the Register's vocabularies only. Permissions:
  `GRANTED / MISSING / STALE`. Interceptors: `RUNNING / PAUSED /
  OFF`. No word crosses families; `STALE` is never a synonym for
  `MISSING` (STALE says the warrant expired; MISSING says a

### 8.3 The engine — the Heartbeat Tap + the Readiness Log

The store is not polled into existence. It is **fed by the services'
own lives, and remembered as events.**

**The Heartbeat Tap (the writers).** Android already polls these
services — it is called binding. The system binds the accessibility
service and the notification listener when they are granted, re-binds
them after death, and calls their lifecycle hooks on every connect
and disconnect; this codebase leaves every hook empty. The Tap wires
them to one process-wide `StateFlow` (Otis's `ReadinessBus`):
accessibility `onServiceConnected` / `onUnbind` / `onDestroy` write
the accessibility item; the listener's connect/disconnect hooks write
its item; the device-admin receiver's `onEnabled` / `onDisabled`
write its item. **The tap itself:** the Shield service's monitor loop
already wakes every **2s**, already computes the enforced package
set, already runs the foreground query — and today throws all of it
away. One publish per iteration puts it on the flow instead: during a
session the blocking facts are *continuously proven*, not sampled.
Grants ride the `GRANT CHECK` hooks of §8.2 (Deck entry + the
existing `ON_RESUME` observer). TIME is never on the bus and never in
the store: it is a pure derivation from wheel + routines state at
render, un-stale-able by construction (§8.5, the strip).

**The Readiness Log (the memory).** Every writer above also appends
one row to an append-only log on the `intercept_logs` pattern —
`(cell, value, atWallMillis, source, pressId)`, heartbeat rows
throttled to at most one per 10s per cell, pruned to a bounded ring
per cell. **State is a query, never a stored field:** the latest row
per item, derived at the instant a surface renders. Because the truth
lives on disk as timestamps, **process death cannot strand a stale
ON**: kill the app for a week, reopen — the first frame derives the
honest state with its honest age, no special case, no cold-start
default. The log is also the receipt's witness (§8.1) and the repair
path's measurer: a bind-flap (`disconnected 03:12:07, reconnected
03:12:09`) is a property of the record, so Suki's stability beat
after a FIX is measured from rows, not timed by hope (§2.6's
hand-back stands: re-sweep ≤300ms + 500ms stability, 90ms cross-fade,
total ≤890ms, no restored line, §8.6). Migration: the log rides
**9→10, the plumbing batch** (Register, Data — append/child table
only, nothing existing changes meaning).

**What dies, entire:** Rosa's 20s standing poll and the whole trigger

### 8.4 STALE — a timestamp query, never a state

`STALE` is **derived at render from timestamps; nobody sets it, no
timer owns it, no loop maintains it.** It cannot fire late, fire
twice, or be left standing by a dead process.

- **The predicate.** An item reads `STALE` when there is **no PASS
  row younger than 45s** for it — its latest measurement is a lack,
  an unknown, or a pass whose warrant has expired. 45s is the one
  threshold, on every surface (the strip's filed 45s, generalised;
  Vau's filed 15,000ms board warrant — three PARK sweeps — is
  superseded: there is no PARK sweep, §8.3, and one threshold or the
  word means two things).
- **Freshness never flatters.** Where an age prints, it is
  **ceiling-rounded to the next 5s** — a measurement 41s old prints
  as 45s old, never 40. Grammar (Rosa's, kept): `JUST NOW` under 5s,
  `OVER 1M` past 55s. Rounding runs against the app, always.
- **Bind silence is evidence, stated exactly.** For a bind-sourced
  item, a set bit with no disconnect event is a *continuously* true
  fact, not a measurement ageing since a connect that may be days
  old — stamping it `OVER 1M` old would be the poller's lie in mirror
  image. So a bind item's measured-instant refreshes at every
  re-validation read (Deck entry, resume, any render after a flow
  change) *on the grounds that the read found the death-event still
  absent* — and the log records that read as its row, so the
  predicate above still governs: if the reads stop (process dead,
  hooks silent), the rows stop, the age grows, and STALE arrives on
  schedule. STALE for a bind item therefore means precisely: *was
  bound; is not confirmed bound now.*
- **Recovery is silent.** One fresh measurement re-warrants the item;
  words re-strike in place on the next render. No "recovered" line,
  no banner, no hand-back ceremony — repair is measured, not
  announced (the PARK exception is the repaired row's own firm click,
  §8.6 — a sound on the row he fixed, not a summons).
