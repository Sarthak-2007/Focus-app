## F1 — Notification persistence [CRITICAL] → OWNED-BY #45

**Current evidence (all quoted from base @ e29acdf):**

- Listener extracts and stores title+body — `MonolithNotificationListener.kt:66-67`:
  `val title = extras?.getCharSequence(Notification.EXTRA_TITLE)?.toString()?.trim().orEmpty()` / `val text = extras?.getCharSequence(Notification.EXTRA_TEXT)?.toString()?.trim().orEmpty()`, inserted at `:77-91` as `CapturedNotificationEntity(..., senderTitle = title.ifEmpty { appRule.appName }, messageBody = text)`. Capture is session-gated and tier-gated (`:72-76`: active session + `resolvedTier != AppBlockTier.OPEN`) — that limits *which* apps, not *how long* or *how safely* rows live.
- Entity is plain strings, no expiry field — `MonolithModels.kt:462-471`: `@Entity(tableName = "captured_notifications") data class CapturedNotificationEntity(... val senderTitle: String, val messageBody: String, val isRead: Boolean = false)`.
- No TTL / prune / cap on storage — `MonolithDao.kt:164-168` has only `deleteCapturedNotification(id)` and `clearAllCapturedNotifications()` (both manual). The `LIMIT 100` at `:147` is display-only on the Flow; the snapshot at `:158-159` is deliberately unbounded (comment `:150-157`: "Deliberately NO LIMIT"). Repo-wide grep: no prune/TTL call site exists for this table.
- Unencrypted, pre-unlock DB — `MonolithDatabase.kt:233` `appCtx.createDeviceProtectedStorageContext() ?: appCtx`, `:237-243` plain `Room.databaseBuilder(storageContext, MonolithDatabase::class.java, "monolith_tactile_db")...build()`. Repo-wide grep for `SQLCipher|SupportFactory|Encrypted` in `app/src/main/java` + gradle files: **zero hits**.
- The honest counterweight still stands: `AndroidManifest.xml:30` `android:allowBackup="false"` and both `backup_rules.xml` / `data_extraction_rules.xml` exclude every domain — the data never leaves the phone; it just never dies on it.

**What #45 (notification-listener) must do — Prisma can cite verbatim:** (1) Add a TTL prune on the insert path and on listener connect, e.g. `DELETE FROM captured_notifications WHERE timestampMillis < :cutoff` with a stated retention (24 h–7 d), plus a hard row cap enforced at insert, not only `LIMIT 100` on the display Flow. (2) Honour sender-side deletion: implement `onNotificationRemoved` and delete the captured row for that notification (requires persisting `sbn.key`/postTime on the entity). (3) Minimise what is stored: the digest's job is "who pinged you during the block" — title-only or truncated body by default; full body only if the user opts in. (4) Address the storage class: either move `captured_notifications` out of the device-protected (pre-unlock) database or state explicitly in the issue why pre-unlock plaintext retention of other apps' message bodies is accepted. (5) Until (1)–(3) land, the digest also resurrects messages a sender deleted-for-everyone — name that in the issue, it is the sharpest user-facing harm.

## F2 — HMAC forgeability [CRITICAL] → OWNED-BY #36

**Current evidence:**

- Hardcoded fallback key — `CryptoIntegrityManager.kt:27-31`: comment `// Deterministic 256-bit fallback keys used when AndroidKeyStore hardware TEE is unavailable (e.g., local JVM tests)`, then `private val fallbackHmacKey = SecretKeySpec("Monolith_Hardware_HMAC_Fallback_32B!".toByteArray(StandardCharsets.UTF_8), HMAC_ALGO)`. **Delta vs audit:** the audit quoted the string as `MonolithHardwareHMACFallback32B!`; the current string is respelled with underscores (`Monolith_Hardware_HMAC_Fallback_32B!`, 36 bytes) — the substance is identical: a public, APK-shipped, forge-anything key.
- Silent downgrade to it — `:64-79`: `signSessionState` uses the fallback when `getHardwareHmacKeyOrNull()` returns null, when `mac.init(hwKey)` throws, and again in the outer catch-all (`:76-79`). No log, no flag, no marker distinguishing a fallback signature from a KeyStore one. `getHardwareHmacKeyOrNull()` itself swallows every exception to null (`:48-50`).
- Blank-signature bypass — `:83-84`: `fun verifySessionState(session: FocusSessionEntity): Boolean { if (session.hmacSignature.isBlank()) return true ...`, and the entity defaults blank: `MonolithModels.kt:279` `val hmacSignature: String = ""`. Verify is load-bearing: `MonolithRepository.kt:741` and `:773` gate session-elapsed/penalty logic on it.
- Threat-model note: the "attacker" here is the phone's owner trying to cheat his own focus lock — which is precisely the adversary this app exists to resist. A forgeable seal breaks the product's core promise, not an edge case.

**What #36 (crypto-integrity) must do — Prisma can cite verbatim:** (1) Delete the hardcoded fallback key and every fallback path in `signSessionState` (`CryptoIntegrityManager.kt:27-31, 64-79`): when no AndroidKeyStore key is available, signing must fail closed (return empty + surface an integrity-unavailable state), never downgrade silently. JVM tests get a test-only key injected, not a production literal. (2) Remove the blank bypass at `:84`: a blank signature on an active session verifies **false**; any legacy unsigned rows are handled by one explicit, logged re-sign-or-invalidate migration, not by a permanent `return true`. (3) Compare with `MessageDigest.isEqual` (the slice's own MEDIUM). (4) Stop claiming "hardware" unless the key's security level is actually checked (no StrongBox/KeyInfo check exists today — slice HIGH #2). Items (1)+(2) are the #68 blockers; (3)+(4) ride the same issue.

## F5 — Exported MainActivity trusts intercept extras [MEDIUM] → HOLDS, Prisma cures

**Current evidence:**

- Exported entry — `AndroidManifest.xml:39-50`: `MainActivity` `android:exported="true"` (`:42`) with only the `MAIN`/`LAUNCHER` intent-filter. Any installed app can launch it with arbitrary extras.
- Blind trust — `MainActivity.kt:126-145` `handleIncomingInterceptIntent`: reads `EXTRA_INTERCEPTED_PACKAGE` (`:128`), `EXTRA_INTERCEPTED_APP_NAME` (`:130`), `EXTRA_INTERCEPT_BADGE` (`:132`), `EXTRA_INTERCEPT_PATH` (`:138-140`) and calls `viewModel.triggerAirlockIntercept(pkg, name, badge, path)` (`:141`). No caller/signature check is possible-or-present, no active-session check, no validation that the package is a blocked app. Constants are plain public strings — `MonolithShieldService.kt:284-291`: `"extra_intercepted_package"`, `"extra_intercepted_app_name"`, `"extra_intercept_badge"`, `"extra_intercept_path"`.
- Effect — `MonolithViewModel.kt:2315-2361` `triggerAirlockIntercept` sets `_airlockState.value = AirlockInterceptState(isVisible = true, interceptedPackageName = packageName, interceptedAppName = appName, interceptReasonBadge = reasonBadge, ...)` unconditionally; the active session is only borrowed for intention text (`:2354`). A spoofed airlock therefore appears **even with no session running**.
- Bounded, honestly: the peek escalation is gated deeper — `InterceptPath.kt` lives at `MonolithAccessibilityService.kt:46-57` (`canHonourPeekLease = this == APP_TIER || this == SHIELD_APP`), and `MonolithViewModel.kt:141-151` `peekOfferFor` additionally requires the named package to be an existing `PEEK_2M` row with cooldown spent and no pill active. So a foreign app can (a) fabricate an airlock for any package/name/badge at any time, and (b) obtain a real 2-minute peek offer only for a package the user already configured as PEEK_2M — by naming it with `path=APP_TIER|SHIELD_APP`, without that app ever being foregrounded or blocked. (a) alone is the finding; (b) is a genuine privilege leak on top.
- Delivery quirk (interacts with #27's top finding): the handler runs only from `LaunchedEffect(Unit)` in `onCreate` composition (`MainActivity.kt:99-101`); `onNewIntent` (`:121-124`) never calls it. The spoof therefore lands on cold start / fresh composition — which is also when a fabricated airlock is most confusing.

**Minimal surgical fix spec (Prisma cures; files sit in #27's area — land as a Prisma PR or hand #27 this spec explicitly; the finding is not in #27's checklist, so do not close #68 as "owned" without one of those two happening):**

- **Tier 1 — revalidation (do this now; ~20 lines, 1 file).** In `MonolithViewModel.triggerAirlockIntercept` (`MonolithViewModel.kt:2315`), before building state: return early unless `activeSession.value?.isActive == true`; look up `apps.value.find { it.packageName == packageName }` and return early if absent or `resolvedTier == AppBlockTier.OPEN`; **derive the badge from the row** (`appEntity.resolvedTier.badge`) and ignore the extra's badge. This preserves both legitimate senders — Accessibility (`MonolithAccessibilityService.kt:197,288-293`: fires only inside the active-session coroutine, for ruled apps) and Shield (`MonolithShieldService.kt:183-188`: fires only during an active session, for a blocked app) — and reduces a foreign spoof to re-showing a truthful airlock for a genuinely blocked app mid-session. *Risk: low. Price: ~20 lines + 1 unit test on the gate.*
- **Tier 2 — provenance nonce (closes the residual + path forgery; ~35 lines, 3 files).** Both internal launchers already converge on putting the same four extras; add a fifth: a single-use nonce (random token + timestamp) written to app-private prefs by the sender (`MonolithShieldService.kt:~183`, `MonolithAccessibilityService.launchInterceptScreen:422-429`) immediately before `startActivity`, and consumed-and-checked in `handleIncomingInterceptIntent` (`MainActivity.kt:126`): missing/stale (>30 s)/replayed nonce → drop the extras, and only a nonce-valid intent may carry a peek-eligible `path` (otherwise force `InterceptPath.UNKNOWN`). This also fixes intent redelivery replay (R2's stale-intent angle) for free. *Risk: medium-low — process death between write and delivery is already the nonce's expiry case; keep Tier 1 as the floor so a lost nonce degrades to a truthful airlock, never a crash. Price: ~35 lines + tests.*
- **Not** the fix: `android:exported="false"` — impossible, the LAUNCHER activity must stay exported. The trust must move from "who sent it" (unknowable) to "is it true + was it minted inside" (Tiers 1+2).

## Signed seats (20)

1. **Crazy-ideas** — Kill the whole class, not the instance: mint intercepts inside the app (single-use nonce, Tier 2) and let the digest store *who* pinged, not *what they said* — a Silence Vault needs envelopes, not opened letters.
2. **Maximum-implementation-potential** — Strongest stack per finding, priced above: #45 TTL+`onNotificationRemoved`+body minimisation, #36 fail-closed signing, #42 disclosure rewrite, #44 policy deletion, F5 Tiers 1+2 (~55 lines total for F5).
3. **Brutal critic** — "Kernel-Level Uninstall Guard" is a lie in two words: nothing is kernel-level and nothing is guarded — `onDisableRequested` returns a sentence. Same theatre in the HMAC: a key printed in the source is not a key, it's a caption.
4. **Improver** — Every finding survives because a truthful version costs almost nothing: one prune query, one deleted literal, one honest string, one removed XML line, ~20 lines of revalidation. Ship the cheap truths first.
5. **Designer** — The consent screens are the product's honesty surface: today the device-admin grant wears the accessibility description (`AndroidManifest.xml:123`) — a user literally cannot consent to what they were never shown.
6. **Consumer** — As a store reviewer I reject this build three ways: AccessibilityAPI declaration vs `strings.xml:4`, device-admin outside permitted use cases, and a notification listener hoarding bodies with no privacy policy in the repo.
7. **Student** — The captured bodies are a student's private chats, OTPs and family messages, kept forever in pre-unlock plaintext (`MonolithDatabase.kt:233-243`) so a digest can show them after study — the retention is the harm, not the feature.
8. **User** — Any junk app on my phone can pop Monolith's airlock over my screen with a fake package and badge, even when I'm not in a session (`triggerAirlockIntercept` never checks). That's not a theoretical spoof; it's a prank API.
9. **User-experience** — All five fixes are invisible when they work: nonce and revalidation add zero taps, TTL pruning changes nothing until the digest is opened. No UX excuse exists for any of them.
10. **Purpose-questioning** — Why does a focus app need to *keep* other apps' message bodies at all? Interruption suppression needs a count and a sender; indefinite body storage serves no stated purpose in the code — it just accumulated.
11. **Thoughtful** — The digest defeats sender-side deletion: a message deleted-for-everyone lives on in `captured_notifications` because `onNotificationRemoved` is never implemented. Keeping what someone retracted is a choice, currently made by omission.
12. **Deep-thinker** — The HMAC's adversary is the user himself — the one adversary with physical access and all the time in the world. Against that threat model a published fallback key + blank-pass (`CryptoIntegrityManager.kt:29,84`) isn't weak crypto, it's no crypto; conversely device-protected storage exists so the shield survives reboot — the fix is retention limits, not pretending the tradeoff away.
13. **Enthusiastic designer** — Honest disclosure can be *good copy*: "Monolith reads your address bar to enforce YOUR site list, and peeks at window text to catch Shorts" is a stronger, more Monolith sentence than the current evasion — the brand is truth-telling machinery.
14. **Wow-level designer** — The app already prints "DATA: ON THIS PHONE ONLY" on its plate and proves it with `allowBackup="false"` + total extraction excludes — then quietly keeps every notification forever. Make the digest worthy of the plate: sealed, expiring, sender-only. That's a feature worth showing off.
15. **Designer with 29 years of experience** — I've watched each of these patterns age: device-admin friction (deprecated, policy-restricted), accessibility-as-blocker (declaration regime since 2022), plaintext pre-unlock stores (the first thing a security review greps). None of these get more acceptable with time; all five are cheapest to fix today.
16. **Intentionality-focused designer** — Every privilege must earn its sentence: `<limit-password/>` has no sentence because it has no purpose. The audit trail of this app is otherwise fiercely intentional — these five are the unexamined defaults, and they read as accidents, not decisions.
17. **Synchronous collaboration** — Routing is the deliverable: F1–F4 duplicate slice findings verbatim, so Prisma must cite the specs into #45/#36/#42/#44 and NOT re-implement them; F5 is in nobody's checklist, so Prisma cures it or hands #27 the spec by name — anything else orphans it.
18. **Implementation-quality** — Caught the drift the audit itself missed: the fallback literal was respelled since `8438f5a` (`Monolith_Hardware_HMAC_Fallback_32B!`, underscores, 36 B) — grep for the audit's exact string returns nothing and would have produced a false FALSE.
19. **Technical execution specialist** — Verified the mechanics, not the vibes: peek forgery is real but bounded by `peekOfferFor` (`MonolithViewModel.kt:147-151`); content *reads* are session-gated at `MonolithAccessibilityService.kt:194-195` though the capability is not; `ls-remote` proves no owning branch exists to hide a fix in.
20. **Interaction-detail specialist** — The spoof's timing is the nasty detail: extras are consumed only on fresh composition (`MainActivity.kt:99-101`) and `onNewIntent` drops them (`:121-124`), so a fabricated airlock arrives exactly at cold start — the moment the user is least able to tell it apart from a real intercept.
