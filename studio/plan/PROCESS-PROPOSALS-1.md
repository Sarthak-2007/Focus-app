## Takt's rulings on the top 5

**Ruling 1 — P-PROBE-4: ADOPT, with its own precondition.** Tier the
merge-train proof: per car, filtered tests for the screens the diff
touches plus the always-on logic classes; the full suite runs once,
after the last car, before SHIP. Any diff touching theme, tokens, or
the ViewModel forces a full suite for that car regardless. Before
the first tiered train, someone times ONE isolated full-suite run —
the audit measured the 15m59s build, never the suite alone, and this
proposal's price stands or falls on that number.

**Ruling 2 — P-FERNROHR-3: ADOPT.** `plan/INTERRUPTS.md` becomes the
only road to Sarthak. Seats checkpoint questions there with options,
what's blocked, and the default if unanswered; Ren empties it in one
batch per natural break; only entries passing Sarthak's own gate go
up. This is the cheapest proposal on the list and it protects the
scarcest resource in the studio — his study block, not our machine.

**Ruling 3 — Rank 3: ADOPT, staged, Massarbeit's form as target.**
Constants move to one DTCG-shaped token file (`plan/register.tokens.json`)
with ruling/code-site provenance in `$extensions`; REGISTER.md
becomes a generated view; a validator fails any build-ready file
whose literals don't resolve to tokens and whose printed sums don't
recompute. Fundus's constants.yaml is the same idea in a weaker
shape — adopt Massarbeit's, credit both. Stage it: migrate first
only the constants that have already generated charges (room, band,
travel, specular, cream, the ARM numbers, the AOD hexes). Big-bang
migration of every constant is explicitly NOT ruled.

**Ruling 4 — Rank 4: ADOPT as ONE build, not four.** A single
Methods-owned checker script (Fundus-2's form) with exactly
Fernrohr-5's four checks v1: (1) REGISTER-CORRECTION passes only
with grep evidence the old value is gone from the governing text;
(2) SHIPPED passes only with a delivery record, else the word is
downgraded to BUILT; (3) BUILD-READY passes only with price, code
sites, and zero open forks; (4) FINDING passes only with file+line
evidence. Failures bounce to the author (CrewAI's guardrail
pattern), max 2 retries, then the coordinator — Ren sees only what
passed, plus escalations. Sicht's Danger framing and Restwert's
poka-yoke checks are the same tool seen from other seats; they fold
in here and do not become separate scripts.

**Ruling 5 — P-SICHT-1 + P-SICHT-4: ADOPT as the review law.**
Stage 6 splits: REQUIRED = S1 only (breaks Sarthak's recorded word,
ships a literal falsehood, or breaks a build). Everything else is
ADVISORY, filed to the record, never held in front of the train.
Deadlines by lazy consensus: advisory findings auto-close at wave
end; S2 auto-closes when the train reaches that screen's car unless
re-filed as S1 with new evidence; S1 never auto-closes and never
expands after the deadline. Sicht-2's prefixes (BLOCKER / Nit: /
Question:) and approve-with-comments become the house style of
advisory findings. This also settles the audit's S2 against
Sarthak's "every screen to everybody" order: it pays as advisory,
and now it is written as advisory.

## All proposals, in ranked order

### 1 · P-PROBE-4: Tier the merge-train proof — filtered suite per car, full suite once per train
- THE WASTE: Stage 7 runs the full suite after EVERY merge; Law 5's train still has 5 unmerged cars — five full-suite runs on the integrator's 2-core machine to land one train, four re-proving screens that car never touched. The audit names merge labour on this compute ceiling as the day's bottleneck; one uncontended build is already 15m59s and suites were load-killed under contention.
- THE FOUND THING: Gradle's official test filtering (`gradle test --tests …`, wildcards, multiple patterns) — https://docs.gradle.org/current/userguide/java_testing.html ; corroborated by Google's managed-devices result caching: https://developer.android.com/studio/test/managed-devices
- THE ADAPTATION: Per car, Ren runs `testDebugUnitTest --tests` limited to (a) classes covering the screens the car's diff touches (mapped from BUILD-CHANGES) plus (b) the cheap logic classes. Full unfiltered suite once, after the last car, before SHIP. A red train-end suite bisects against the per-car greens already on record. Lane-side stage-5 proof unchanged.
- COST: ~30 min to write the screen→test-class mapping from the current 8-class set. Real risk: a cross-screen regression escapes its car's filtered run and is caught only at train end — mitigated by the shared-code rule (theme/tokens/ViewModel diff = full suite for that car).
- EXPECTED SAVING: (cars − 1) × full-suite duration per train = 4 runs avoided on the current train; ~20 min/train if the suite measures 5 min, ~8 if it measures 2. Stands or falls on timing one isolated suite run first.

### 2 · P-FERNROHR-3: One checkpointed interrupt queue for Sarthak — questions batch, work resumes, nothing bursts

### 3 · P-MASSARBEIT-3: REGISTER becomes a validated token file — one value per constant, generated into code (converged: P-FUNDUS-4)
- THE WASTE: PA-S1-04: the register prints the losing value as law in ≥6 places (TRAVEL 180dp, SPECULAR's swept form + LUTs as shipped truth, BAND 85.5/77.5 "operative" with 73.5/65.5 only in an amendment, CREAM "provisional" after ratification, B-12 "pending ratification"). PA-S1-03: room 796dp in both governing documents, its printed stack sums to 604, the adopted 821 in neither. PA-S1-09: `#758F88` printed where the token is ARGB `0x758F8888` — a byte-transcription fork. S2: sixteen plan hexes have no register literal at all; the register carries zero prices.
- THE FOUND THING: W3C Design Tokens format (DTCG, stable 2025.10) — `$value`/`$type`/aliases/`$extensions`, schema at design-tokens.org; Style Dictionary (Amazon) as compiler with first-class DTCG support in v4 (pin the implemented draft); JSON Schema (Draft 2020-12) as the contract layer — https://cobalt-ui.pages.dev/guides/tokens ; https://norbix.dev/posts/json-schema/
- THE ADAPTATION: Source of truth becomes `plan/register.tokens.json`: one token per constant — value, type, description, `$extensions{ruling, codeSite, supersedes, price}`. JSON key uniqueness makes "two values for one constant" unrepresentable. REGISTER.md becomes a rendered view. A stage-3 validator fails a build-ready file if (a) a literal appears that is not a token/alias, (b) printed arithmetic doesn't recompute from token values, (c) a colour token's channels violate the never-green rule after ARGB expansion. Kotlin constants are generated from the token file; builders import `Tokens.ROOM_TOTAL_DP`, never transcribe.
- COST: The migration is the real cost (~half a day over both documents, and it will surface latent forks — that is the point, but it is a stage-2 wave in itself). Style Dictionary's 2025.10 support is incomplete — pin v4's draft or keep a small own generator. Builders lose "just write the number."
- EXPECTED SAVING: Structurally prevents (not detects) the transcription/supersession class: the six PA-S1-04 instances and the 796/821 fork cannot recur — one full critic-charge → correction → re-verification cycle saved per occurrence, 6+ occurrences in one day's audit. A token can still hold a wrongly DECIDED value; decision quality stays with stage 2.
- CONVERGED — P-FUNDUS-4 (same mechanism, YAML shape): constants in one machine-readable file, REGISTER generated from it ("never edit generated files" — Dive into Deep Learning's contributor discipline: https://d2l.smola.org/chapter_appendix-tools-for-deep-learning/developers-guide.html ; n-skills' `sources.yaml` registry: https://deepwiki.com/numman-ali/n-skills/6-maintainer-documentation). Derived sums stop being hand-typed. Takt's ruling: adopt Massarbeit's DTCG form (it also generates the Kotlin side); Fundus-4 is the on-ramp if DTCG tooling stalls.

### 6 · P-WAAGE-1: Per-build timing ledger — every Gradle run times itself (Talaiot)
- THE WASTE: The audit's only build numbers are one critic's one-off measurement (2 cores, 7 GB, load 6.84 pre-build, one uncontended build 15m59s). Law 3's two-compile cap rests on a single anecdote (three concurrent builds turned a 2-minute compile into 25). No per-build/per-lane/per-task timing record exists, so nobody can say which task, lane, or contention level eats the morning — or whether the cap is the right number.
- THE FOUND THING: Talaiot (cdsap/Talaiot v2.1.0) — Gradle plugin tracking task/build durations with custom publishers — https://github.com/cdsap/Talaiot/ ; fallback: Gradle `--profile` / Build Scan (https://docs.gradle.org/current/userguide/inspect.html). Waage files median/p95, slowest-5 tasks, contended-vs-solo ratio at each wave close.
- COST: One pinned plugin dependency (first build per lane downloads it), a small publisher class to maintain, and a mandatory overhead check against the 15m59s baseline — if it adds measurable time on 2 cores, drop to `--profile` + parser.
- EXPECTED SAVING: The compile-cap decision becomes arithmetic: if contention really costs ~10×, the cap stays and is priced; if one task (Robolectric? a compile task?) eats the build, the fix is that task. Saves nothing until someone acts on the slowest-task list — stated by the seat itself.

### 7 · P-PROBE-2: Robolectric diet — one sandbox config, NATIVE only where pixels are read, capped forks
- THE WASTE: The trunk test set carries ≥3 distinct Robolectric configurations across 8 classes / 24 tests (harness: sdk 36 + NATIVE + custom qualifiers; TetradRenderTest: NATIVE, no @Config; ExampleRobolectricTest: sdk 36, no graphics mode), plus logic tests (ledger, week, migration) that never read a pixel yet pay sandbox construction. Robolectric's architecture: a Sandbox with its own classloader is built per configuration — diversity is paid repeatedly on a machine already load-killed at 3 lanes.
- THE FOUND THING: Robolectric GraphicsMode API — LEGACY is "no-ops and fakes," NATIVE is native rasterization: an opt-in cost — https://robolectric.org/javadoc/4.10/org/robolectric/annotation/GraphicsMode.Mode.html ; sandbox mechanics: https://chromium.googlesource.com/external/robolectric/ ; Gradle Test task docs (`forkEvery` default 0; low non-zero "can severely hurt performance"): https://docs.gradle.org/current/userguide/java_testing.html
- THE ADAPTATION: (1) One shared `robolectric.properties` / base `@Config(sdk=[36])`; NATIVE pinned only on the two render classes, LEGACY explicit elsewhere. (2) Classes that never touch View/Bitmap/Compose move off RobolectricTestRunner to plain JUnit (audit ledger/week/migration first). (3) `forkEvery = 0` explicitly, `maxParallelForks = 2` with per-fork heap caps, gated by Law 3's flags so forks parallelize only when no second lane compiles.
- COST: 1–2 h of config/runner edits + one before/after timing run. A "logic" test secretly depending on shadows fails when moved — it moves back individually, reason logged.
- EXPECTED SAVING: External shape of the cost: first test in a class ~10.4 s sandbox vs ~0.44 s subsequent (illustrative, not our machine). Bounded: 0.5–3 min per suite run, plus the probabilistic dominant term — every suite run that no longer gets load-killed saves an entire rerun.

### 8 · P-FERNROHR-1: A Refinery seat owns the merge queue — Ren only signs the push
- THE WASTE: The audit's named bottleneck: "code lands through one builder at a time" (BUILD-CHANGES 06:40, 06:55); the token merge deferred twice; every ruling one hand. Law 1's origin: three bases cost an hour of hand-merging. Doubling seats "doubles only input — not throughput."
- THE FOUND THING: Gas Town's Refinery (Steve Yegge) — a dedicated merge-queue processor: receives MERGE_READY, rebases branches onto target, runs quality gates, squash-merges one at a time through a serialised merge slot, reports MERGED / MERGE_FAILED — https://yegge.ai/gastown ; https://deepwiki.com/steveyegge/gastown/3.5-refinery
- THE ADAPTATION: Split stage 7. A standing Refinery seat owns the published train: per car it rebases the lane diff onto its named base, resolves mechanical conflicts, runs the suite, files a one-page merge packet (diff summary, suite result, conflicts touched). Ren's only act: read the packet, sign MERGED or return MERGE_FAILED with a reason. Laws 1/5 unchanged; the labour moves.
- COST: One coordinator-grade seat permanently on queue work; the packet gate must be built and trusted before Ren steps back; if Ren re-checks packets in full, the saving evaporates.
- EXPECTED SAVING: Up to the documented ~1 h/morning of hand-merging plus the deferred-merge class — realistically 30–60 min of Ren's hands per day, until a week of packets proves the gate.

### 9 · P-GITTA-1: Make the merge train a tracked stack with git-spice — restack instead of hand-rebase
- THE WASTE: Same bottleneck as rank 8, at the tooling layer: lanes return loose diffs against named frozen bases; when car 1 lands and trunk advances, every downstream car's rebase is Ren's bespoke archaeology (1 hour lost to divergent bases in one morning, PIPELINE Law 1).
- THE FOUND THING: git-spice (`gs`) — GPL-3.0 Go tool for stacking branches on plain Git: `gs stack restack`, `gs upstack restack`, `gs repo sync`; works offline, no SaaS, no GitHub dependency — https://github.com/abhinav/git-spice ; https://abhinav.github.io/git-spice/
- THE ADAPTATION: Lanes return named branches in train order, tracked once by Ren (`gs branch track`). Trunk advance → `gs stack restack` rebases downstream cars mechanically. A stage-6 fix to car 2 → `gs upstack restack`, not a manual cascade. Ren still sets order and checks every diff; the rebase labour under the law changes, not the law. Cost of entry: lanes must commit as branches, not folder copies.
- COST: Low — one binary, `gs repo init` per tree, ~half a day to trial on one real train and write the lane brief lines. Free — fits free-routes-only.
- EXPECTED SAVING: Unproven here; bounded to the documented class — if it removes half the hand-rebasing on a train day, tens of minutes per train. Does not touch the compute ceiling.

### 10 · P-SICHT-5: Bors/GitHub merge queue for the train — review approves, the queue lands
- THE WASTE: Stage 7 is local and manual end-to-end; PA-S1-19 shows the hand-tracked state failing (six "SHIPPED" labels, two deliveries). Law 8 already states the failure mode: if everything waits on Ren, the pipeline has failed.
- THE FOUND THING: Bors (Graydon Hoare, for Rust, 2013) — on approval, merges into a staging branch, runs the full suite, fast-forwards main only if green, bisects batches on failure — the "Not Rocket Science Rule"; GitHub's native merge queue is the built-in equivalent — https://mergify.com/blog/the-origin-story-of-merge-queues ; https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/merging-a-pull-request-with-a-merge-queue
- THE ADAPTATION: Law 5's order becomes a literal queue: a car enters when stage-5 proof is green and no S1 is open (rank 5's law); a script driving the existing private-Gradle-home lanes (respecting Law 3's two-compile cap) tests trunk+car, lands it if green, kicks only a failing car to the back with its failure letter while later cars keep moving. Ren spot-checks diffs in batch instead of serialising every merge.
- COST: Highest of Sicht's five — queue script, staging-tree handling, Laws 1/3 compliance; a flaky queue becomes a second bottleneck. Bors-ng is maintenance-mode; adopt the design, not the codebase. The queue creates no compute — it stops wasting it on stale-base re-tests.

One trace per build-ready item / train car; spans for the 8 stages, harvested retrospectively from artifacts that already exist: build-ready file mtime, rank-6 build ledger + flag-file times (BUILD/PROOF), mail/ timestamps (REVIEW), BUILD-CHANGES + delivery records (MERGE/SHIP). WORD/WAVE spans stay blank until their artifacts carry timestamps — gaps are data too. Waage's harvester writes `swarm/metrics/stages.csv` at wave close and per-car queue analytics (wait = merge-started − proof-complete, Ren-labour per car, bounce rate) into METRICS.md; Restwert publishes one wait-vs-work board per train in the Waste Ledger. The harvester glue is HOMEGROWN (nearest inspiration: the OTel CI patterns) and is judged as such.
- COST: One script + per-artifact parsers that break when formats drift; Restwert ~15–20 min of coarse (letter-time) bookkeeping per train. Ambiguity to settle up front: queue-entered = PROOF-complete moment, not lane-claimed readiness, or lanes will game it.
- EXPECTED SAVING: A measurement, not a saving — within 2–3 trains it replaces pace arguments with one number (wait share of lead time) and decides the question impossible today: whether "Ren alone merges" is a quality gate worth its wait, or the ceiling itself. Must be read with bounce rate, never wait alone — faster merging of bad diffs is worse.

### 26 · P-PROBE-1: Paparazzi pilot — take the static renders off Robolectric entirely
- THE WASTE: Every render pays the full Robolectric price: the harness runs `@GraphicsMode(NATIVE)` + sdk 36, builds a real Room DB + ViewModel per method, polls up to 45,000 ms for seeding, and burns ~10 s of literal `Thread.sleep` settle time per run — to produce mostly static pictures of 5 screens for review, on a VM measured at load 6.84 pre-build with a suite already load-killed at 3 lanes.
- THE FOUND THING: Paparazzi (cashapp/paparazzi) — renders Views/Compose on the JVM via LayoutLib (the Android Studio preview engine), no emulator, no Robolectric sandbox; `recordPaparazziDebug` / `verifyPaparazziDebug` — https://raw.githubusercontent.com/cashapp/paparazzi/master/README.md
- THE ADAPTATION: Pilot only, one screen first (Tasks or Vault — least custom-drawn): add the plugin, a `DeviceConfig` matching the harness's `w412dp-h915dp-xhdpi`, snapshot tests fed fixed fake UI state instead of live ViewModel/Room seeding. The Robolectric harness stays the merge-gate render for anything Paparazzi renders differently — Deck's wheel/specular Canvas work is the named fidelity risk (LayoutLib is not native graphics). Pixel-match converts a screen; divergence keeps it on Robolectric permanently, no argument.
- COST: ~½–1 day: plugin + catalog wiring, fake-state fixtures per screen, one golden re-record, one side-by-side fidelity audit. Goldens are a second image set to maintain until a screen fully converts.
- EXPECTED SAVING: Certain: up to 90 s of seed-polling (45 s × 2 methods) + ~10 s of sleeps per harness run, plus one sandbox boot per converted class. Beyond that unmeasured: 1–5 min per suite run if 3+ of 5 screens convert; 0 if the fidelity audit fails, in which case the pilot dies at the cost above.

### 27 · P-PROBE-5: One managed-device smoke per ship batch — and why the emulator/cloud candidates mostly lose here
- THE WASTE: Everything above proves renders on the JVM; on-device behaviour (blocking, haptics, routine firing) stays "unproven until his phone," and device-class failures are discovered at the most expensive point — by Sarthak, after shipping.
- THE FOUND THING: AGP managed devices — declared in Gradle, created/booted/torn down by AGP, using emulator snapshots for fast startup and clean state, plus test-result caching — https://developer.android.com/studio/test/managed-devices . Evaluated and rejected as primary: Firebase Test Lab's free Spark tier caps at 10 virtual + 5 physical runs/day and past-free is Blaze billing ($1/virtual-hour, $5/physical-hour) — paid, out of scope (https://firebase.google.com/docs/test-lab/usage-quotas-pricing) ; Karumi Shot is emulator-based (GPU `swiftshader_indirect`) — full emulator boot for what snapshots exist to avoid (https://raw.githubusercontent.com/pedrovgs/Shot/master/README.md).
- THE ADAPTATION: Declare exactly one managed local device (one Pixel profile, target API) and one small instrumented smoke test — launch, navigate all 5 destinations, assert no crash — run once per merge train at stage 8, solo per Law 3, never per lane or per car. Firebase's free Spark quota (≤10 virtual runs/day) is an occasional second opinion before a big ship, never pipeline infrastructure.
- COST: ~half a day: managed-device DSL, system-image download (disk fine, RAM is the constraint — the run serializes against everything), one smoke class. Adds wall-clock minutes to each train's ship step by design.
- EXPECTED SAVING: 0 min per suite run — this proposal SPENDS time, stated plainly by the seat. Downstream and unmeasured: ~5–10 min of manual emulator setup saved per ship batch, and device-class failures move from "found by Sarthak on his phone" to "found on the VM before the batch ships." If the smoke proves flaky after two trains, kill it; the phone remains the bench, as today.

### 28 · P-GITTA-3: Pre-flight the train with git-branchless — speculative merges and per-commit `git test`
- THE WASTE: Stage 7 runs the full suite serially per car after each merge, on the measured ceiling (load 6.84 pre-build, 15m59s uncontended, a suite already load-killed at 3 lanes). Ren's check-every-diff duty × a full suite per car is the merge stage's fixed cost; conflicts are discovered IN Ren's merge, not before it.
- THE FOUND THING: git-branchless (arxanas/git-branchless) — on plain Git: smartlog, restack, undo, sync, plus speculative merges (pre-computed conflict warnings) and `git test` (runs a command across a commit stack in parallel worktrees, with result caching) — https://github.com/arxanas/git-branchless
- THE ADAPTATION: Before the train runs, the LANE (not Ren) runs speculative-merge checks against the trunk it will actually meet (Law 5's promise, made verifiable) and files the result in its closing letter — a predicted-conflict car is fixed in the lane. Ren runs `git test` across the stacked cars once; unchanged cars hit the cache instead of re-paying the full suite. `git test --jobs` is set to respect Law 3's two-compile cap.
- COST: Low–medium — install + `git branchless init` per repo; no workflow change for lanes that ignore it. Main cost: Ren learns the smartlog/restack vocabulary; one trial wiring `git test` to the Android test task inside worktrees with private Gradle homes.
- EXPECTED SAVING: Unproven for the Android suite. Bounded by arithmetic: a 7-car train implies up to 7 serial full-suite runs at stage 7; avoiding even two redundant runs at the 15m59s build figure is ~30 min of wall-clock IF the cache hits. If every car touches shared files, saving is near zero and the honest output is the speculative-merge warning alone.

### 29 · P-GITTA-4: Land the train through GitHub's native stacked PRs (`gh stack`)
- THE WASTE: Stage 7/8 are local and manual; what has landed lives in Ren's head and a hand-maintained log — PA-S1-19: six builds labelled SHIPPED, two files delivered. The merge order, per-car diff, and landed state have no single factual home.
- THE FOUND THING: GitHub Stacked Pull Requests, public preview 30 Jul 2026 — each PR targets the branch below, shows only its layer's diff, upper PRs auto-rebase/retarget when a lower layer merges, and merging the top ready PR lands it and every unmerged layer beneath in one operation — https://github.blog/changelog/2026-07-30-stacked-pull-requests-are-now-in-public-preview/ ; CLI: `gh extension install github/gh-stack`. Hard limit: all branches in the same repository.
- THE ADAPTATION: The train is published as a stack on the (already private) `Sarthak-2007/Focus-app` repo, linked bottom-to-top in Law 5 order. Stage 6 reviews per-layer diffs (each car shows only its own change — Law 6's overlap made literal). Ren lands approved bottom layers in one operation; what has merged becomes a fact of the repo, not of BUILD-CHANGES prose. Local copied-tree building (stage 4, private Gradle homes) unchanged — only return and merge move onto branches.
- COST: Medium, with stated risk: public preview (subject to change; merge-queue support still rolling out at announcement) and lanes must push branches to GitHub instead of handing back folder diffs. No money cost. Fallback is rank 9 (git-spice), which needs no host support.
- EXPECTED SAVING: Unproven and preview-dependent: retarget/rebase bookkeeping minutes per car on a 7-car train (tens of minutes per train day) plus elimination of the mislabelled-shipped error class. No reduction in Ren's check-every-diff duty; per-layer GitHub CI does not help the local Gradle ceiling.

### 30 · P-GITTA-2: Run lanes on Jujutsu (jj) over the Git trunk — automatic rebase and undo for the integrator
- THE WASTE: Law 1 buys merge safety by freezing lanes to stale bases ("never rebases mid-build"), deferring ALL divergence cost to Ren at stage 7 — where the audit found it: bespoke archaeology, an hour lost to three divergent bases in one morning.
- THE FOUND THING: Jujutsu (martinvonz/jj, Rust, von Zweigbergk/Google) — Git-compatible: uses the existing `.git` store, its commits are real Git commits; working-copy-as-a-commit, automatic rebase of descendants when a parent changes, first-class conflicts, an operation log giving full undo — https://github.com/martinvonz/jj
- THE ADAPTATION: Trunk stays Git in `Focus-app/`; the GitHub repo changes not at all. Each lane tree runs `jj git init --colocate`; the lane's work is a stack of jj changes on the frozen stamp. When trunk advances mid-build, jj rebases descendants automatically on the next command instead of the lane being forbidden to move; conflicts surface as first-class conflict commits the lane resolves. Ren gets `jj op log` / `jj undo` — a bad merge becomes one undo. Per-tree opt-in: lanes that hate it keep plain Git on the same repo.
- COST: Medium — jj is explicitly experimental (its own docs say so); every lane agent needs a new mental model (change IDs, no staging area): realistically 1–2 days of friction and one pilot lane before trusting it on a train. Colocated-mode behaviour with Gradle/private Gradle homes is untested here and must be trialled, not assumed.
- EXPECTED SAVING: Unproven — no honest minutes figure exists until a pilot train is timed against a Git-only train, and the seat says so. The mechanism attacks the deferred-divergence cost: if automatic rebase keeps 3–4 lanes continuously current, Ren's per-car conflict work shrinks toward true semantic conflicts only.

### 31 · P-GITTA-5: Sapling `sl absorb` for stage-6 fixups — review corrections land in the right car automatically
- THE WASTE: Stage 6's overlap (Law 6) means findings amend cars mid-stack — but amending an early car invalidates every car above it, and today that restack is Ren's hand labour at stage 7, competing with the merge queue itself (review output already outruns execution: B-4 HELD, six corrections unlanded).
- THE FOUND THING: Sapling (Meta; github.com/facebook/sapling; sapling-scm.com) — Git-interoperable, stack-first (`sl pr submit`), and `sl absorb`: working-copy edits are folded automatically into the correct ancestor commit by line provenance, restacking descendants.
- THE ADAPTATION: Narrow adoption only — NOT a VCS switch. The builder lane for a stacked change works in Sapling on its Git-backed tree; when a finding targets code written three cars down, the builder edits at the top of the stack and runs `sl absorb` — the hunk routes to the commit that introduced those lines and the stack restacks, instead of a manual checkout-amend-replay of the cars above. Ren's stage-7 check becomes a before/after stack diff (smartlog, one view).
- COST: Medium–high for a narrow win, stated honestly: a second VCS dialect for lane agents, overlapping-PR shapes its own docs warn confuse the plain GitHub UI, and design scale (Meta monorepo) this repo doesn't have. Trial cost: one lane, one real fixup cycle; studio-wide adoption is not proposed.
- EXPECTED SAVING: Unproven. Per fixup, one command replaces amend-and-restack — minutes per fixup, scaling with stack depth and fixup frequency, both unmeasured in our logs. At one or two mid-stack fixups per train day the saving is single-digit minutes and does NOT justify the learning cost; it pays only if Law 6 makes mid-stack fixups routine — count them on the next train before adopting.
