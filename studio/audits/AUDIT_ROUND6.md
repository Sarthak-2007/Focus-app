# Focus-app (Monolith) — Brutal Audit, Round 6: Borrow-and-Do-Better + Fresh Loss Hunt

Scope: losses only. Every finding below is a place Monolith loses to a named rival system (reverse-engineered from that rival's APK) or a fresh defect found in Monolith's own code — no Monolith wins, no ties, no rival flaws with no Monolith gap. Borrow findings each carry a design for beating the original's implementation, not just copying it. Store-presence and monetisation findings are excluded by standing order: nothing here is about listings, discoverability, pricing or paywalls; every finding is about the product itself. Deduped against all 1,731 findings of Rounds 1–5 (title-similarity sweep plus substance review; 18 of 155 reported findings were cut as repeats of earlier rounds or of each other). ## Part 1 — Borrow and do better (68 findings — 6 critical, 45 high, 17 medium, 0 low)

#### [CRITICAL] Monolith must borrow YPT's behaviour-typed group challenges (sit / wake / sleep) — and prove them with signed session receipts instead of server honour-system

YPT EVIDENCE.md §7: group challenges ship as a dedicated feature family with three behaviour-typed proof forms — sit/stay, wake-up and sleep — evidenced by disjoint help/example sets (group_challenge_help_image1–10, sit_challenge_example1–6, wake_challenge_example1–6, assets/challenge/sleep.png), member presence states (assets/group/member/ic_user_{on,off,out,fire,smoke,sweat}.png) and groupID/chatID push payloads (§3.5). Its documented weaknesses: challenge rules live entirely in the unextracted Dart layer (§14, unknown), enforcement underneath is UsageStats polling plus overlay with an unknown poll period (§3.4), and all state is server-held — Firebase project yeolpumta-ko plus Pallo's own *.pallo.cn APIs (§10) over a manifest with usesCleartextTraffic=true (§1) — so a 'proof' is whatever the server is told, with no on-device signed artefact. Monolith has no challenge, group or shared-goal entity at all: MonolithModels.kt's entity list (focus_tasks:100, blocked_apps:231, focus_sessions:267, routines:549) contains nothing social, and the only 'challenge' in the codebase is the solo exit-friction DisarmChallengeState (MonolithViewModel.kt:193). What Monolith does have, and YPT does not, is a verifiable proof object: FocusSessionEntity carries hmacSignature (MonolithModels.kt:279), evidenceMask (:317), shieldGapSeen (:355) and routineOutcome (:314) — a session already knows whether the shield actually held.

Recommendation: Borrow the typed-challenge primitive, not pooled minutes: add ChallengeEntity (type SIT/WAKE/SLEEP, window start/end, daysMask reusing RoutineSchedule math at MonolithModels.kt:571, loadoutName) and ChallengeProofEntity (challengeId, sessionId, verdict). SIT = a sealed session overlapping the window with shieldGapSeen=false; WAKE = a session whose startWallTimeMillis falls inside the wake window; SLEEP = a session under the existing SLEEP SmartLoadout (MonolithModels.kt:54) spanning the night window. Beat YPT on proof: the proof object is the session's existing signed receipt — receiptNumber (MonolithModels.kt:371) plus hmacSignature plus gap/evidence fields — exported as a shareable, offline-verifiable proof card/QR that any member's app can verify locally against the shared challenge key, instead of YPT's model where the verdict exists only as a row on Pallo's server reached over cleartext-permitted traffic. Beat it again on honesty: a session with shieldGapSeen=true or a VALVE_BROKE finish prints FAILED on the proof itself, where YPT's polling detector (§3.4, period unknown) can be left 'recording' on a desk while the user lives on a second device and the server never knows. No account or server is required for a challenge to run — proofs exchange peer-to-peer — which removes YPT's Firebase-plus-.cn backend as a single point of trust and failure.

#### [CRITICAL] Graded verdicts are undecomposable: attended seconds are computed from hidden evidence arcs no surface can show

Monolith already computes a graded verdict in secret: computeAttendedSeconds (MonolithRepository.kt:959) unions five-minute coverage arcs (EVIDENCE_COVERAGE_MILLIS = 300_000, MonolithRepository.kt:139) around intercept instants, task completions and evidence stamps, and finaliseRoutineSession turns that number into ATTENDED / PARTIAL / MISSED — yet no surface anywhere lists which instants contributed, what the arcs covered, or why a window graded as it did. Opal, for all its opacity, at least ships an explainer per sub-score: Focus, Sleep and Rest each carry their own explanatory text (Opal EVIDENCE.md §9.1). Monolith's one real computed grade has not even prose — it is a black box that stamps an immutable outcome (routineOutcome is written once and never re-judged) the user cannot audit.

Recommendation: Ship a verdict ledger: every graded number in the app becomes tappable into its decomposition — the contributing evidence instants with timestamps, the arc each one bought, the floor and yardstick applied, and the formula version, recomputed on-device from the stored rows so the decomposition must reproduce the stamp or flag the row. Beat the original on its documented weakness: Opal's explainers are prose wrapped around a formula whose weights are not in the APK and may be server-side (Opal EVIDENCE.md §9.1, §15) — an explanation that cannot be checked. Monolith must not repeat that: no explainer text without the arithmetic underneath it, and because session rows already carry an HMAC signature (FocusSessionEntity.hmacSignature), the decomposition can be verified against signed rows offline — proof, not narration.

#### [CRITICAL] Borrow and beat Opal's Sick Day Pass: make the emergency valve a witness-approved request with the reason decided before release, not read after it

Monolith: MonolithRepository.kt:2214-2246 completeEmergencyBreak() is a purely local transaction — it checks the week's spends, inserts an EmergencyBreakSpendEntity and disarms, with no second person anywhere; MonolithRepository.kt:117 fixes EMERGENCY_BREAK_REASON = "Emergency Break" (a constant, never free text) and MonolithModels.kt:442-450 shows the spend row carries only sessionId, instant, week anchor and heldSeconds=60. Rival: Opal EVIDENCE.md §10.3 — the Sick Day Pass is a rationed stock of day-long unblocks where the user picks a reason (Feeling sick / Doctor or dentist / Family emergency / …) plus a free-text note that 'Your school will be able to read this'; §8.2 — the personal Emergency Pass likewise self-redeems once per week. In both, the authority reads the justification only after the block is already gone; nobody approves anything.

Recommendation: Turn the valve into a witness request, not a self-spend. Spending the weekly token opens a request carrying the user's typed reason and the minutes asked for; a pre-named witness approves or denies before the seal breaks, the request auto-expires unanswered after a short deadline, and a second named witness forms a fallback quorum so one unreachable phone cannot strand a genuine emergency. The grant, denial or expiry is booked onto the spend row itself (reason, decider, decision instant), so the ledger that already exists (MonolithModels.kt:442-450) becomes an accountability record instead of a bare count. This beats Opal's documented weakness: a self-service pass whose reason is read after the fact by an institution — Monolith's version makes the reason the price of the decision, decided before release, by a person the user chose.

#### [CRITICAL] Borrow Opal/ScreenZen QR pairing, beat their cloud dependence: an offline witness countersignature pinned at seal time makes the receipt verifiable by a third party

Monolith: CryptoIntegrityManager.kt:27-30 ships a deterministic fallback HMAC key as a public string constant ('Monolith_Hardware_HMAC_Fallback_32B!') and :63-78 falls back to it whenever the KeyStore key is unavailable, so the session signature proves nothing to anyone who has read the APK; AndroidManifest.xml:6-14 declares no INTERNET permission and no component exports a receipt, and MonolithModels.kt:382-390 shows the receipt number is just a counter claimed inside a local transaction. Rivals: Opal EVIDENCE.md §4.1/§10.4 — QR surfaces exist (opal://qr, applink /qr, /invite-friend, /join-school) but verification rides on Firebase Auth/Firestore and an account; ScreenZen EVIDENCE.md §7 — Halo join is a QR/deep-link flow, yet 'sign-in is required to claim/manage a Halo' and 'To connect and sync Halo settings to the cloud, an internet connection is required'. Flipd EVIDENCE.md §5 — its published sessions can be manually added (FLPAddTimeActivity) and edited after the fact (FLPEditSessionActivity), so its social record is a diary, not proof.

Recommendation: Add an in-person countersigning protocol built for a sealed, offline app. At seal time the phone renders a QR holding the session id, receipt number, held app/site counts (MonolithModels.kt heldAppsAtSeal/heldSitesAtSeal) and a hash of the seal snapshot; the witness's phone scans it and pins that hash. At finish, a second QR carries the outcome and elapsed span, and the witness countersigns it with a locally generated keypair — no account, no server, no INTERNET permission added. Anyone holding the witness's public key can verify the pair offline. This beats both originals' documented weaknesses: Opal and ScreenZen make witnessed proof depend on accounts and cloud sync that fail offline, and Flipd's feed ranks records the owner can edit by hand — Monolith's countersigned slip is uneditable because the witness pinned the seal before the session ran.

#### [CRITICAL] The seal signs only the session's first five fields — the finished receipt's claims (outcome, elapsed, held counts, deflections, receipt №) are signed by nothing

Monolith: CryptoIntegrityManager.kt:53-81 — signSessionState() builds the signed payload as exactly five ARM-time fields (startWallTimeMillis|startElapsedRealtimeMillis|bootCount|targetDurationSeconds|isStopwatch) and every call site (MonolithRepository.kt:1339,1428,1864,1957) is a start/resume path; nothing re-signs at finish. The ending write stamps the claims the receipt actually prints — outcome classification, endWallMillis, heldAppsAtSeal/heldSitesAtSeal, receiptNumber (MonolithModels.kt:324-368) and the deflection list (ReceiptState.kt:135-183) — with no signature over any of them, so the finished record's contents are protected by nothing. Rival: Blockit signs the asset that leaves the device — its parachute count is signature-protected and syncs taking max(server, local) (blockit-re/EVIDENCE.md §7.3).

Recommendation: Borrow Blockit's instinct — sign the portable asset, not the local timer — and beat it: add a second, finish-time seal that signs a canonical serialisation of the full ReceiptState (session id, receipt №, outcome word, arm/end wall times, sealed elapsed, held apps/sites counts, deflection count, break seconds, shield-gap and fault flags) at the same write that classifies the outcome. Do not repeat Blockit's documented failure mode: on signature mismatch Blockit silently resets the count ('getParachuteCount: signature mismatch, resetting', §7.3) — Monolith's finish seal must fail closed, marking the receipt FAULTED and unpublishable as clean, never quietly re-minting a valid-looking slip over edited fields.

#### [CRITICAL] No asymmetric credential exists: the symmetric KeyStore secret can never be shown to a verifier without handing them the power to forge, so no offline, accountless QR proof is possible

Monolith: the only key is a symmetric HMAC secret in AndroidKeyStore (CryptoIntegrityManager.kt:26-27,36-52) — verification requires the secret itself, so no third party can ever check a receipt without being handed the means to forge one; worse, verifySessionState returns true for a blank signature (CryptoIntegrityManager.kt:83-84) and silently falls back to a source-committed key (CryptoIntegrityManager.kt:29-33). Rival: Opal already puts a QR surface at the centre of cross-device trust — deep links opal://qr and https://applink.opal.so/qr, and Settings → 'Scan QR code — Connect to another device' (apk-re/opal/EVIDENCE.md §4 line 58, §10.4).

Recommendation: Borrow Opal's QR as the transport and invert its purpose: Opal's QR only pairs the phone into Opal's own account/Firebase/Mac ecosystem (§10.4: Firebase Auth, Firestore, Cloud Functions in the path) — it proves membership, not a session. Monolith should mint an Ed25519 device keypair at first seal, print the public-key fingerprint on every receipt, and encode the finish-sealed payload (finding above) as a QR plus a copyable text block. Any second Monolith install — or a standalone verifier with no account, no server and no network — scans and checks the signature offline. The verification path must contain no vendor server and no sign-in: that is the beat over Opal, whose proof dies with its backend.

#### [HIGH] No pre-focus wind-down module: Monolith seals cold from the Deck, where Forest runs a timed Relax breathing session that hands off into the plant

Forest EVIDENCE.md §7 documents a complete pre-focus module: Room tables relax_sessions(id, theme_id, target_relax_duration, relax_interval_start, relax_interval_end, auto_start_focus_session, plant_request_id) and breath_events(id, action, time, relax_session_id), a dedicated RelaxHostActivity, its own audio manager (AndroidRelaxAudioManager) and an end-of-relax notification (ScheduleRelaxSessionEndsNotificationUseCase). Its documented weaknesses: it is a silo — separate activity, separate onboarding, a second audio stack duplicating the focus BGM machinery — and the breath_events it logs have no evidenced consumer: the Plants schema (§5.1) carries no relax-adherence field, so the breathing record never reaches the session it prepared. Monolith has nothing in this space at all: FocusSessionEntity (app/src/main/java/com/example/data/MonolithModels.kt:267) has no pre-phase columns, a session is born cold inside MonolithRepository.startSession (app/src/main/java/com/example/data/MonolithRepository.kt:1321) straight from the seal tap in MonolithViewModel.armMonolithSession (app/src/main/java/com/example/ui/MonolithViewModel.kt:2197), and the one audio engine is contractually barred from the sustained sound a guided breath needs — TactileSoundEngine's design law states 'Zero ambient sound mixer loops' (app/src/main/java/com/example/service/TactileSoundEngine.kt:31). The only rest Monolith knows is the in-session Safe Break (MonolithModels.kt:283), which is a parole window between blocks, not a way in.

Recommendation: Borrow Relax as a phase of the session Monolith already has, not as a second app. Add a wind_down phase ahead of the seal inside the existing Deck/sequencer flow: a new relax_sessions table keyed to FocusSessionEntity.id (theme, target duration, interval start/end, breath target) plus a breath_events table (session id, action, timestamp) written by the breathing surface. Pace the breath with a bounded ambient-loop channel added to TactileSoundEngine — one loop voice with a hard duration cap, exempted from the one-shot law only for this phase — instead of Forest's duplicated second audio manager. Beat the original on the two points its own schema exposes: (1) consume the breath record Forest throws away — completed/target breaths are computed at phase end, stamped onto the session row, entered in the session's evidence mask and printed on the receipt, so wind-down adherence is part of the session's signed record; (2) no silo — no separate activity, onboarding or settings surface; the phase is configured from the same arm screen that sets duration and blocks, is skippable only as a recorded outcome (WIND_DOWN_SKIPPED on the row, never a silent absence), and ends in the chained start described by the plant_requests mechanism rather than dropping the user back on a home screen to seal by hand.

#### [HIGH] No deferred session-start queue: a Monolith session can only begin by an immediate seal tap or a recurring routine, where Forest persists plant_requests that start a session when their moment comes

Forest EVIDENCE.md §7 documents a persisted deferred-start queue: table plant_requests(id, trigger_at, state), created for a relax session by CreateImmediatePlantRequestForActiveRelaxSessionUseCase and gated by IsEligibleForAutoFocusUseCase — a session can be materialised later by a stored request row rather than by a tap at start time. Its documented limits: the queue is welded to the Relax module, the only evidenced creation path is the 'immediate' one, and whether a request is eligible to fire is decided by a use-case whose criteria are not determinable from the APK — a black box between the user's intent and the start. Monolith has no equivalent object: sessions originate only from an immediate seal (MonolithRepository.startSession, app/src/main/java/com/example/data/MonolithRepository.kt:1321, sealed by sealSession at :1414) or from recurring routine windows, and RoutineScheduler (app/src/main/java/com/example/service/RoutineScheduler.kt:41) uses AlarmManager only to arm routine boundaries. No one-shot start-request entity exists anywhere in MonolithModels.kt, so 'seal me in at 19:00', set at 17:00, is inexpressible — the user must be present and tapping at the moment focus is supposed to begin.

Recommendation: Borrow plant_requests as a general, first-class start_requests entity: (id, trigger_at, state PENDING/FIRED/EXPIRED/CANCELLED, created_from, and a frozen snapshot of intention, loadout name, duration, block count and task bond taken at request time). RoutineScheduler's existing AlarmManager path (RoutineScheduler.kt:41-60) arms the trigger and MonolithBootReceiver re-arms pending requests across reboot, so the queue survives the phone dying — the failure mode Forest delegates to library reschedulers. On firing, the request runs the identical startSession + sealSession transaction as a manual seal, so a deferred start gets the same HMAC signature, held-apps/held-sites snapshot and receipt number as a tapped one; nothing about a fired session is second-class. Beat Forest on its two documented weaknesses: (1) generality — requests can be created from the Deck ('seal at…'), chained from the wind-down phase, or attached to a routine window, not only from one module; (2) no eligibility black box — the state machine is the whole contract, every transition is stamped on the row, and a request whose trigger passes unfired (shield permissions revoked, another session active) lands as EXPIRED with the reason on the record instead of silently never starting. The frozen snapshot also closes a live Monolith hole: later loadout edits cannot rewrite what a pending start will enforce.

#### [HIGH] No fractional quick-unlock lane: Monolith must borrow ScreenZen's half-open-priced Quick Unlock and daily open-budget ledger

ScreenZen EVIDENCE.md §4: Quick Unlock is a shorter unlock lane that 'Counts as 0.5 opens' against a Daily Open Goal, and the daily counter's reset time is user-configurable (info_reset_app_opens_time). Its documented weaknesses: the goal is honour-system by default — 'Unless you select strict block below, you can still exceed your daily opens' — the 0.5 price is flat forever, and counting rides the 500 ms UsageEvents polling loop (§3.5), whose exact cadence is unknown (§21). Monolith has no priced lane at all: its only relief is PEEK_2M, a fixed 120-second lease plus a mandatory 20-minute cooldown (MonolithModels.kt:25-29; MonolithRepository.kt:106-108), identical for the 1st and the 40th reach. BlockedAppEntity already stores interceptCount (MonolithModels.kt:240) and two peek-lease timestamps (:241-242) but no open-budget, no fractional debit and no reset anchor; dailyLimitMinutes (:238) is a minutes figure, never an opens count.

Recommendation: Add an append-only OpenBudgetLedger entity modelled on EmergencyBreakSpendEntity (MonolithModels.kt:443-450): every unlock writes a debit row (packageName, spentAtWallMillis, dayAnchorMillis stored at debit time so clock travel cannot re-book the day, debitHalfUnits). Two lanes on BlockedAppEntity: a 30-second quick-check priced at 0.5 opens and the existing 120s peek priced at 1.0, both written by MonolithShieldService's lease check (MonolithShieldService.kt:170-171) and the accessibility door. Beat the original three ways: (1) the price escalates with the day's accumulated debits (0.5 → 1 → 2 half-unit steps), where ScreenZen charges a flat 0.5 forever; (2) the daily cap is hard by default and only soft if the user explicitly chooses advisory mode, inverting ScreenZen's exceed-by-default goal; (3) the reset anchor is a per-app user-set hour stored on the ledger row, and the day's debits fold into the session receipt's existing HMAC-signed record, so the budget is auditable proof, not a poll-derived counter.

#### [HIGH] Blocked sites dead-end at BACK plus a wall: Monolith must borrow ScreenZen's custom redirect destination for blocked websites

ScreenZen EVIDENCE.md §6: on a website block, the accessibility service redirects the browser to a user-chosen custom URL (info_custom_blocked_website_url), falling back to screenzen.co. Its documented weaknesses: the target is one global URL for every site and context, the fallback is the vendor's own marketing page, and the redirect is fire-and-forget — nothing records it, and nothing stops an immediate Back/retype. Monolith's site door has no destination at all: on a domain match MonolithAccessibilityService.kt:256-273 fires GLOBAL_ACTION_BACK and launches the intercept screen, dumping the user into the Airlock with nowhere productive to go. The data model cannot express a destination either: BlockedSiteEntity is a bare domain string and nothing else (MonolithModels.kt:544-547).

Recommendation: Add a redirectTarget column to BlockedSiteEntity (per-site, editable in ShieldMatrixScreen's site editor) plus a GuardSettingsEntity default, and change the §4 branch of MonolithAccessibilityService (MonolithAccessibilityService.kt:256-273): on a match, instead of BACK + Airlock, navigate the browser to the site's target — defaulting to a Monolith deep link that renders the session's declared intention and active task, never a vendor page. Beat the original: (1) the target is per-site and per-context, not one global URL; (2) every redirect writes an InterceptLogEntity row with outcome REDIRECTED, so the receipt counts redirected reaches separately from returned ones — ScreenZen records nothing; (3) the redirect carries a 60-second return lease: re-entering the same domain inside the lease escalates to the full Airlock with the peek withheld, closing the Back-and-retype hole a bare redirect leaves open.

#### [HIGH] No pixel-level content detection: Monolith reads only accessibility view IDs and text nodes, so any app that renders without them is invisible — it must borrow StayFree's screenshot-plus-OCR screen-text layer

StayFree's accessibility sensor is configured for total screen access: typeAllMask events, flagRetrieveInteractiveWindows|flagReportViewIds, canRetrieveWindowContent=true, and canTakeScreenshot=true in its res/xml-v22 config variant, and the APK bundles ML Kit OCR for screen-text recognition — the machinery behind its keyword blocking and in-app feature blocking (EVIDENCE.md §3, §4, §9, §14). Its weaknesses are documented in the same file: the screenshot capability exists only in the v22 config variant, and the OCR/capture stack's evidenced home is the Sensor Tower collection pipeline — collected ads, purchases and screen content, remote-config page-view allow-lists, a screenshots=false remote-config default — with §16 admitting the consumer blocking behaviour of that stack is unknown statically. Monolith has no pixel channel at all: app/src/main/res/xml/accessibility_service_config.xml subscribes only to typeWindowStateChanged|typeWindowContentChanged with canRetrieveWindowContent=true and no screenshot capability, and every content decision in MonolithAccessibilityService.kt is a view-ID or text-node lookup — detectShortsOrReelsFeed matches five hardcoded view IDs (MonolithAccessibilityService.kt:332-351), the site blocker reads five hardcoded URL-bar view IDs (MonolithAccessibilityService.kt:384-390). A game, a canvas/Flutter-rendered feed, or text baked into an image exposes none of those nodes, so Monolith's keyword and in-app rules silently cannot fire there.

Recommendation: Borrow the capture layer, beat the collection layer. Add canTakeScreenshot to accessibility_service_config.xml and a PixelProbe step in MonolithAccessibilityService: when node-based inspection of a package that carries keyword/in-app content rules yields no readable text, take exactly one frame via AccessibilityService.takeScreenshot, run ML Kit OCR on-device in memory, match the existing keyword/feature rules against the recognised text, and discard the frame in the same call — never written to disk, never uploaded (Monolith has no network stack to upload it with). Log only rule id, package and timestamp into InterceptLogEntity (MonolithModels.kt:451) so the sealed receipt can cite the capture as evidence. This beats the original on its own documented terms: StayFree's capture is a dual-purpose collection sensor with a remote-config kill switch (screenshots=false) and an isAccessibilityTool=false declaration, while Monolith's is sealed-session-only, single-purpose, user-auditable per capture in the intercept log, and structurally incapable of exfiltration.

#### [HIGH] Notification holding exists only inside an armed session: Monolith must borrow StayFree's standalone, always-on Blocking Notifications as standing per-app rules

StayFree ships Blocking Notifications as an independent feature — a dedicated StayFreeNotificationListenerService suppresses notifications from blocked/limited apps whenever the feature is configured, with no session, limit expiry or Focus Mode required (EVIDENCE.md §4 item 5, §10). The original's weakness is documented in §16: whether its blocked notifications are deleted or merely suppressed is unknown statically, and the evidence shows no sender granularity, no digest and no release schedule — suppressed notifications go somewhere unaccounted. Monolith's listener is session-gated by construction: in MonolithNotificationListener.kt, onNotificationPosted loads getActiveSessionSnapshot() and returns if there is no session or it is not active, and only then holds notifications for non-OPEN tiers — outside an armed session it holds literally nothing, and there is no notification-rule entity anywhere in MonolithModels.kt (the @Entity tables are blocked_apps, blocked_sites, focus_sessions, routines, guard_settings, captured_notifications and others, none of them a standing notification rule).

Recommendation: Add a NotificationRuleEntity (target package or category, mode HOLD/ALLOW, optional daily window, release time) to MonolithModels.kt/MonolithDao.kt and evaluate it in MonolithNotificationListener.onNotificationPosted before the active-session check, reusing the existing CapturedNotificationEntity storage and cancelNotification path. Held items release into the existing post-session digest at the rule's release time or the next session end, whichever comes first, and every hold/release is counted on the receipt. Beat the original on its documented unknowns: where StayFree's suppression fate is unaccountable (deleted vs suppressed unknown, no digest), Monolith's is a hold-and-release queue with a guaranteed return path; and because CapturedNotificationEntity already stores senderTitle, add a per-sender allow-through on a rule (a named person breaks through, the app's promo noise does not) — a granularity the evidence never shows in StayFree's package-level feature.

#### [HIGH] No routine-conflict detection at save time: overlapping routines are saved blind and the loser is silently held at runtime

AppBlock EVIDENCE.md §4.1: a dedicated SchedulingConflictUseCase and ConflictingSchedulesExplanationActivity exist, plus a schedules_limit_warning string warning that schedules may fail to activate when there are too many distinct intervals (background-refresh system limit). Its weakness: detection is a side explanation surface, the overlapping schedules are still saved, and the runtime precedence rules in §4.2 are scattered hint strings (time overrides usage/launch unlocks, usage-limit lock persists past launch allowance) rather than a resolution the user chose. Monolith has nothing at any layer: MonolithViewModel.kt:1501-1513 persistRoutine() — the single save funnel for every routine edit — only re-stamps scheduleEditedAtMillis and reconciles; MonolithViewModel.kt:1530-1545 adjustRoutineTime() validates nothing beyond a 30..1080-minute span clamp. Two enabled routines with overlapping windows and different loadouts save silently, and RoutineDerive.kt:159 then quietly returns OPEN_HELD when another session overlaps the window — the second routine is starved with no word to the user at save time or fire time, and its window is still judged from that silent collision.

Recommendation: Borrow the conflict check and beat the side-activity design by putting it in the save path itself: add a pure RoutineConflictDetector (start/end/daysMask/loadoutName are all on RoutineEntity, MonolithModels.kt:550-571) called inside persistRoutine() before repository.updateRoutine. On overlap with a different loadout, the ShieldMatrixScreen routine editor refuses the silent save and forces one of three explicit, stored resolutions — MERGE (union the windows under the stricter loadout), SPLIT (trim the new routine's mask/minutes to the free remainder), or STACK_DENIED with the exact colliding minutes printed. Persist the choice as a conflictResolution column on RoutineEntity so RoutineDerive never has to improvise OPEN_HELD for a collision the user already adjudicated. Also borrow the interval-budget warning and beat it: because Monolith runs one chained alarm (RoutineScheduler), render a live 'distinct windows per week: N' meter in the editor that turns red before the chain's reliability is at risk, instead of AppBlock's passive warning string discovered after failure. Also borrow AppBlock's density honesty: when the live routine set's distinct schedule boundaries approach what the OS background-refresh/alarm budget can actually fire, say so at save time (its schedules_limit_warning) instead of letting routines silently fail to activate.

#### [HIGH] No guess-vs-reality baseline: first run never shows the user their actual last 7 days, and no stored baseline exists for later receipts to measure against

AppBlock EVIDENCE.md §10: onboarding asks Q2/Q3 (guessed daily phone time, guessed daily checks/unlocks), then Q4 requests Usage Access explicitly 'to prepare this report for you' and generates a personalised 7-day report — daily average screen time, most-used apps, daily unlocks — printed against the guesses (intro_time_more_than_guess='%d%% more than your guess'). Its weakness: the report is a one-shot conversion artefact — nothing in the evidence shows the baseline or the guesses being stored, re-compared after blocking starts, or feeding any later screen; it is UsageStats screen-time only, with no temptation/intercept data. Monolith never makes the ask or the comparison: MonolithRepository.kt:532-545 queryRealTodayUsageMinutes() reads only a trailing 12-hour window for today's per-app minutes, compute7DayHistory() (MonolithRepository.kt:2361-2391) aggregates only Monolith's own session rows — a first-run user with zero sessions is shown zeros — and no entity anywhere stores a guess or a pre-Monolith baseline (grep for guess/baseline in app/src/main/java returns no feature code).

Recommendation: Borrow the guess-vs-reality reveal as the first-run flow on TactileDeckScreen and beat the one-shot design by making the baseline permanent state: (1) ask the two guesses, (2) on Usage Access grant, extend the existing queryUsageStats INTERVAL_DAILY pattern at MonolithRepository.kt:534-545 to 7 days and build the report (daily average, top-5 apps, unlocks where available), (3) persist it as a new BaselineEntity (guessedMinutes, actualMinutes, per-app minutes JSON, capturedAtMillis) in MonolithModels.kt beside GuardSettingsEntity.
